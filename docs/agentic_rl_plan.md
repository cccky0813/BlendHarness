# 后训练计划 v3：用可验证奖励训练一个"场景编辑"小模型（EditRL）

> v3（2026-10-30）取代 v2（10/25 的"部件修正"方案）。取代原因见第 13 节。
> 这份文档写得比较细，每一节都先解释用到的概念，再讲具体做法，可以当学习笔记用。

## 0. 一句话

把 **Qwen3-1.7B** 训练成一个"脚本编辑器"：输入**一份已有的 Blender 场景脚本**和**一句修改需求**，输出**只改必要地方**的编辑操作。训练分两步：

1. **SFT**：先用老师模型（DeepSeek）的正确解做模仿学习；
2. **GRPO**：再用强化学习继续训练，奖励**全部由程序计算**：
   - 脚本能不能跑通；
   - 要求的改动有没有做到（`expectations.py`）；
   - 有没有改坏不该动的东西（`regressions()`）。

预算：AutoDL 显卡约 ¥250 + API 约 $15–25，大约 3 周。

## 1. 先把几个基础概念讲清楚

### 1.1 什么是"后训练"

一个大模型的训练大致分两段：
- **预训练**：在海量文本上学"下一个词是什么"，学到语言和世界知识。这一步要几千张卡，我们不碰；
- **后训练**：在预训练好的模型上，用少得多的数据，把它调成"会按要求做事"的样子。常见的三种：

| 方法 | 数据长什么样 | 学到什么 | 一句话理解 |
|---|---|---|---|
| **SFT**（监督微调） | （输入，标准答案）对 | 模仿标准答案 | 照着老师的作业抄，学会格式和基本做法 |
| **偏好学习**（RLHF / DPO） | （输入，好回答，差回答） | 更像好回答、更不像差回答 | 需要人或模型来判断"哪个更好" |
| **RLVR**（可验证奖励的强化学习） | 只要题目和一个**能自动判分的程序** | 自己试、按分数调整 | 自己做题、对答案、记住做对的路子 |

我们做的是 **SFT + RLVR**。RLVR 是 DeepSeek-R1 之后最热的方向，适合"答案能被程序检验"的任务，比如数学（对答案）、代码（跑测试）。我们的任务正好也能被程序检验：跑 Blender，再看检查是否通过。

### 1.2 为什么不只做 SFT

SFT 只能学到老师**做过的**解法，而且老师的错误也会一起学进去。RL 让模型**自己尝试**，按真实的结果（奖励）调整，可以：
- 超过老师在某些方面的表现，比如更克制、回归更少；
- 学会老师数据里没有覆盖到的情况。

但 RL 有个前提：**模型得偶尔能做对**。如果一道题模型试 8 次全错，就没有"做对的样子"可以强化。所以先用 SFT 把模型拉到"有时能做对"的水平，再用 RL 提高。这就是"先 SFT 热身，再 RL"的常见套路。

### 1.3 GRPO 是怎么工作的

GRPO（Group Relative Policy Optimization）由 DeepSeekMath 论文提出，是目前 RLVR 最常用的算法。核心步骤（每一步训练）：

```
1. 取一批题目（比如 16 道）
2. 每道题让模型生成 G 个回答（比如 G = 8）      ← "一组"
3. 每个回答都算奖励（我们这里：跑 Blender + 检查）
4. 在每组内部比较：
      优势(第 i 个回答) = (奖励_i − 本组平均奖励) / 本组奖励标准差
   比平均好的回答优势为正，差的为负
5. 更新模型：增加优势为正的回答的概率，降低优势为负的
```

和更早的 PPO 相比，GRPO **不需要另外训练一个"价值模型"**来估计"这道题平均能得多少分"，而是直接用同一道题的 8 个回答的平均分作为基准。省掉一个模型，就省了一大半显存，所以单卡也能跑。

几个训练时会看到的关键词：
- **组内全对或全错**：8 个回答奖励都一样时，标准差为 0、优势全为 0，这道题对训练没有贡献。要统计这种组的比例：比例太高说明题目太难或太简单。常见做法是直接过滤掉这些组（DAPO 论文里的"动态采样"）；
- **KL 惩罚**：限制新模型和原模型差得太远，防止训练跑偏。近来的很多工作把它设成 0 或很小；
- **clip（裁剪）**：每一步对每个 token 概率的调整幅度设上限，防止一步走太远（PPO 和 GRPO 都有）；
- **熵**：模型输出的"随机程度"。熵掉得太快说明模型过早只会一种答法（探索不足）。

### 1.4 LoRA 是什么，为什么用它

完整微调要更新模型的全部参数。1.7B 参数在训练时，加上优化器状态，大约要 20GB 以上显存，再加上生成回答用的 vLLM，24GB 的 4090 放不下。

**LoRA**：冻结原模型，只在每层旁边加两个很小的矩阵（秩 r，比如 32）来学"改动量"。要训练的参数只有原来的不到 1%，显存需求大幅降低。代价是效果通常比完整微调略差，v2 方案里引用过相关结论。在 ¥500 的预算下这是合理的取舍，报告里如实写明即可。

### 1.5 vLLM 和 TRL 是什么

- **TRL**：HuggingFace 的后训练库，提供 `SFTTrainer` 和 `GRPOTrainer`，我们直接用；
- **vLLM**：一个专门做快速生成的推理引擎。GRPO 的大部分时间花在"生成 8 个回答"上，用 vLLM 能快好几倍。TRL 的 GRPO 可以和 vLLM 跑在同一张卡上（colocate 模式）。

### 1.6 reward hacking（钻奖励的空子）

模型会找**最容易拿分的办法**，不一定是你想要的办法。经典例子：只检查"测试通过"，模型就学会把测试删掉。我们这个任务里可能出现的空子，以及对策，写在第 4.3 节。**能讲清楚自己是怎么防、怎么发现 reward hacking 的，是这类项目在面试里最有含金量的部分。**

### 1.7 pass@k

一道题让模型做 k 次，**至少有一次做对**的概率。
- pass@1：一次就做对的能力；
- pass@8：给它 8 次机会能不能做对，代表模型"潜力"的上限。

GRPO 的作用大致是把 pass@8 范围内"偶尔能做对"的题，变成 pass@1 也能做对。所以训练前先看 pass@8：如果太低（比如低于 10%），RL 学不到东西，要先 SFT 或换更大的模型。

## 2. 任务定义

### 2.1 输入（prompt）

```
系统提示：你是 Blender 脚本编辑器……只输出编辑操作……
当前脚本：（一份能跑通的 bpy 脚本，约 150–300 行）
修改需求：Make the cottage roof red, like clay tiles.
```

### 2.2 输出

和 BlendHarness 的 `edit_script` 工具同一个格式：一组精确替换。

```json
{"edits": [
  {"old_string": "M_ROOF = mat(\"RoofTiles\", (0.45, 0.16, 0.12))",
   "new_string": "M_ROOF = mat(\"RoofTiles\", (0.62, 0.12, 0.08))"}
]}
```

**为什么用这个格式，而不是输出整份新脚本：**
1. **输出短**：一般几十到几百个 token，整份脚本要几千个。GRPO 每步要生成 8×16 = 128 个回答，输出越短，训练越快、越便宜；
2. **天然鼓励"只改必要的地方"**，和回归惩罚的方向一致；
3. 和 BlendHarness 的 Coder 用同一个工具格式，训练好的模型可以直接接回系统。

`old_string` 必须在脚本里**恰好出现一次**，否则这次编辑无效。规则和 `edit_script` 完全一样，直接复用它的代码。

### 2.3 为什么是单步，不是多轮 agent

真正的 agentic RL 是让模型自己调用工具、看结果、再调整，一条轨迹要跑很多次 Blender、生成很多段文字，算力成本是单步的好几倍，¥500 做不了。单步编辑是这个方向上**最小、但完整**的版本，多轮放在第 12 节"之后"里。

## 3. 数据：编辑任务怎么造

### 3.1 原材料

`runs/` 下一共有 318 份能跑通的 `final_script.py`。其中 90 份是多轮会话里同一个场景的连续几轮，彼此很像；**真正可用作起点的是 228 份单次建模的脚本**（内容互不相同的有 225 份，长度中位数约 150 行，最长 507 行），涵盖家具、房间、村庄、街道等各种场景。这些就是"当前脚本"的来源，不用花钱。

每份脚本出 3–4 道题，就能得到第 3.4 节需要的约 1000 道题。不过很多建模是同一道题的重复运行（评测时每题跑多次），场景种类比 225 少，按场景划分 train / test 时要按**题目来源**分组，不能只按文件分。

### 3.2 生成流程（每份脚本）

```
① 出题：DeepSeek 读脚本 + 场景快照，提出 3 个编辑需求，每个附：
      expect   （检查这个需求做到了没有，用 expectations.py 已有的检查类型）
      touches  （允许改动的物体名模式）
② 解题：DeepSeek（老师）对每个需求输出编辑操作
③ 验证（全部由程序完成）：
      a. 原脚本必须【不满足】expect          ← 否则"什么都不改"也能拿分
      b. 老师的解：能应用、能跑通、满足 expect、没有回归
      c. 检查能被判定：没有"无法判定"的项
   全部通过的题才保留
④ 人工抽查：随机看 50 道，确认需求、检查、touches 三者一致
```

第 ③a 步非常重要，它直接堵住了最大的一个空子：**如果原脚本本来就满足检查，模型什么都不改也能拿满分**。

### 3.3 编辑类型（出题时要求均匀覆盖）

| 类型 | 例子 | 主要检查 |
|---|---|---|
| 改颜色或材质 | 屋顶改红 | `material_hue` |
| 新增物体 | 在井边放一个桶 | `exists`、`near`、`grounded` |
| 删除物体 | 拆掉栅栏 | `absent` |
| 移动 | 把路灯挪到斑马线旁 | `near`、`direction` |
| 改尺寸 | 左边的台灯高一点 | 尺寸、`above` |
| 改数量 | 树从两棵变三棵 | `count`、`evenly_spaced` |

### 3.4 规模和划分

| 集合 | 规模 | 用途 |
|---|---|---|
| train | 约 800 题 | SFT 和 GRPO |
| dev | 100 题 | 训练过程中看效果、选检查点 |
| test | 150 题 | 最终结果，只用一次 |

**按场景划分**：同一份原脚本出的题只进同一个集合，测试集里的场景模型都没见过，测的是泛化能力，而不是"背过这个场景"。

### 3.5 成本

DeepSeek（`config/prices.json`）：flash 每百万 token 输入 $0.3、输出 $1.2；v4-pro 输入 $1.32、输出 $3.96。
- 出题用 flash：约 1000 份 × 8k 输入 ≈ 8M token，约 $3；
- 解题用 v4-pro：约 1500 道 × 6k 输入 + 1k 输出，约 $18；
- 合计约 **$20**。按 50% 的筛选通过率，最后剩 800–1000 道可用的题。

## 4. 奖励函数

### 4.1 计算过程

```
1. 解析输出：不是合法 JSON，或者没有 edits           → 格式错误
2. 应用编辑：有 old_string 找不到或不唯一            → 编辑无效
3. 在 Blender 里运行改后的脚本：报错                → 运行失败
4. 拿到场景快照，计算：
      完成度  c = 通过的 expect 数 / expect 总数
      回归数  g = regressions(改前快照, 改后快照, touches) 的数量
```

### 4.2 奖励公式（第一版，训练前用老师的解和人工抽查校准）

```
格式错误 / 编辑无效      → −1.0
运行失败                 → −0.5
否则：
  reward = 1.0 × c                     （做到了多少）
         + 0.5 × [c == 1]              （全部做到的额外奖励）
         − 0.3 × min(g, 5) / 5         （回归惩罚，最多扣 0.3）
```

几点设计理由：
- **分级的失败惩罚**：格式错误比运行失败更差，给模型一个"先学会格式，再学会跑通"的梯度；
- **部分分（c）+ 全对奖励**：只给全对奖励的话，大部分回答都是 0 分，组内没有差异，学不到东西；有部分分，"做到了 3 项里的 2 项"也比"1 项"好，信号更密；
- **回归惩罚有上限**：如果不封顶，一次大回归会扣到很低的分，模型可能学会"宁可不改"；封顶后，只要做到了，就一定比不做好；
- 这些系数**不是拍脑袋的定论**，第 7 节有专门的消融实验来检验。

### 4.3 可能被钻的空子，以及对策

| 空子 | 表现 | 对策 |
|---|---|---|
| 什么都不改 | 输出空的 edits | 原脚本必然不满足检查（第 3.2 节 ③a），所以得 0 分，不会被奖励 |
| 推倒重写 | 把整个场景重新写一遍 | 回归惩罚；另外输出格式是"替换"，大段替换会很长，也更容易出错 |
| **改名骗检查** | 加一个叫 "Fence" 的空物体，或者一个极小的方块，让 `exists("fence")` 通过 | **最需要防的一个**，因为我们的检查是按名字匹配的。对策：检查时要求匹配到的物体有合理的几何（顶点数、尺寸下限）；评测时用 LLM 裁判抽查渲染图，对比"程序说通过"和"裁判看到的" |
| 把颜色改到刚好过线 | 色相刚好落在范围边缘 | 无害，可以接受 |
| 删掉检查涉及的旧物体再重建 | 名字变了，检查照样通过 | 回归检查会把"被删掉的旧物体"算作回归 |

训练时**每隔 N 步人工看几条高分样本**，专门找"分高但其实做得不对"的例子。找到了就是很好的分析素材：在报告里写"发现了什么空子、怎么修的奖励"。

### 4.4 奖励计算的速度

一次 Blender 运行约 1–3 秒（无头模式、不渲染，只取快照）。GRPO 每步 128 个回答：
- 开 8 个 Blender 进程并行，每步的奖励计算约 30–50 秒；
- AutoDL 的 4090 实例一般带 16 个左右的 CPU 核，够用。

奖励计算的代码复用 BlendHarness 的沙箱（`sandbox/session.py`）和检查（`analysis/expectations.py`），在 Mac 上先写好、测好。

## 5. 模型选择

**主模型：Qwen3-1.7B**，用非思考模式。我们要的是短的编辑输出，思考模式会生成很长的推理过程，拖慢训练。

上服务器之前，先在 dev 集上测原版模型（用 vLLM 生成，可以先租几个小时卡，或者用 API）：

| 情况 | 怎么办 |
|---|---|
| pass@8 < 10% | 题太难：必须先 SFT；SFT 之后还低，就换 Qwen3-4B |
| pass@8 在 10%–80% | 理想区间，SFT 热身之后做 GRPO |
| pass@8 > 80% | 题太简单：加难度（多步编辑、组合需求） |

## 6. 训练

### 6.1 SFT（热身）

| 参数 | 值 | 说明 |
|---|---|---|
| 数据 | train 集里老师的正确解，约 800 条 | 只用通过验证的解 |
| 方法 | LoRA，r = 32，alpha = 64，作用在所有线性层 | |
| 学习率 | 1e-4，余弦衰减 | LoRA 的学习率一般比完整微调高 |
| 轮数 | 2 epoch | 数据少，多了容易过拟合 |
| 序列长度 | 最长 8k token | 脚本 + 需求 + 输出 |
| 时间 | 4090 上约 1–2 小时 | |

SFT 之后在 dev 集上测一次：格式正确率应该大于 95%，完成率比原版明显提高。

### 6.2 GRPO

| 参数 | 值 | 说明 |
|---|---|---|
| 起点 | SFT 之后的模型 | |
| 每步题数 | 16 | |
| 每题回答数 G | 8 | |
| 学习率 | 5e-6（LoRA） | |
| KL 系数 β | 0（再试 0.01） | |
| clip | 0.2 / 0.28（上下不对称） | DAPO 的做法，给"概率低但做对了"的回答更多提升空间 |
| 温度 | 1.0 | 保证组内回答有差异 |
| 最长输出 | 1024 token | 编辑操作用不了这么长 |
| loss | 按 token 平均 | |
| 过滤 | 去掉组内奖励全相同的组 | |
| 步数 | 约 300 步（约 6 个 epoch） | 看 dev 集曲线决定何时停 |
| 时间 | 4090 上约 10–15 小时 | 生成和奖励计算各占一半左右 |

### 6.3 训练时要盯的曲线

| 曲线 | 正常的样子 | 不正常说明什么 |
|---|---|---|
| 平均奖励 | 稳步上升 | 一直不动：学习率太小或题太难；突然跳升：先怀疑钻了空子 |
| 组内全同的比例 | 逐步上升（题被学会了） | 一开始就很高：题目难度不合适 |
| 输出长度 | 平稳或缓慢下降 | 暴涨：模型在灌水；跌到很短：可能在"少改"上钻空子 |
| 熵 | 缓慢下降 | 掉得很快：探索不足，需要提高温度或增大 clip 上限 |
| 回归率 | 下降 | 上升：回归惩罚太弱 |
| dev 集完成率 | 上升后趋平 | 训练奖励涨、dev 不涨：过拟合到训练题 |

## 7. 评测

### 7.1 主表（test 集，150 题，场景都没见过）

| 模型 | 格式正确 | 能跑通 | 完成率（全部检查通过） | 回归率 | 平均奖励 |
|---|---|---|---|---|---|
| 什么都不改（下界） | 100% | 100% | 0% | 0% | 0 |
| Qwen3-1.7B 原版 | | | | | |
| + SFT | | | | | |
| + SFT + GRPO | | | | | |
| DeepSeek v4-pro（老师） | | | | | |
| Sonnet 4.6（上限参考，只跑 test） | | | | | |

完成率报 pass@1（贪心解码）和 pass@8；每个数字都带 95% 置信区间（按题 bootstrap）。

### 7.2 消融实验（每组都是一次 GRPO，约 10–15 小时）

| 实验 | 回答的问题 |
|---|---|
| **去掉回归惩罚** | 回归惩罚是不是真的在起作用？预期：完成率差不多甚至更高，回归率明显上升。**这是最重要的一组**，直接对应"只改要改的地方" |
| 只给全对奖励（去掉部分分 c） | 部分分是不是让学习更容易？预期：训练更慢，组内全同的比例更高 |
| 跳过 SFT，直接 GRPO | SFT 热身有多必要？（只有原版 pass@8 足够高时才做） |

预算只够做 2 组，优先做前两组。

### 7.3 质量抽查（防止"程序说通过、其实不对"）

从 test 集里每种模型抽 30 题，渲染改前和改后的图，交给 LLM 裁判（gpt-5.5）判断"需求做到了没有"，再和程序检查的结论对比。对应第 4.3 节的"改名骗检查"：如果 GRPO 模型在"程序通过、裁判不通过"上明显多于 SFT 模型，就说明它学会了钻空子。

## 9. 代码组织

```
rl/
  tasks.py        出题、解题、验证（第 3 节）→ data/{train,dev,test}.jsonl
```
