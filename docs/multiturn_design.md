# 多轮续写建模：设计文档（v1.1）

> 2026-10-26。目的：让 BlendHarness 支持"用户持续提需求、在已有场景上继续修改"，并建立一套**程序检查 + LLM 裁判**两层的多轮测评。
> 状态：**设计已确认主要方向，还没有写代码。**
>
> **v0 → v1**：去掉"每轮重建"策略；重新设计上下文与记忆管理（第 5 节）；新增 LLM-as-judge 效果评测（第 6.2 节）；把 workflow 的改造细化到文件和阶段（第 4 节）。
> **v1.1 → v1.2**：对照实验从 4 组减为 3 组（去掉"只有账本"），组件改用各自的指标测；M3 只跑 1 次（5.7、6.5）。
> **v1 → v1.1**：明确需求是逐轮输入的，系统看不到后面的轮次（4.5）；会话增加前置条件和模拟用户补充实验（6.1、6.5）；参考业界做法重写裁判指标（6.2）；M3 纳入第一版，用 SQLite 加向量检索实现，并设计检索本身的测评（5.9）；第 10 节改为决定记录。

## 1. 为什么做

| 证据 | 说明 |
|---|---|
| 修复后的新基线（RSI 笔记第 7 站） | 单轮、单件家具或小场景上，Sonnet 第 0 轮每次只有 0.2–0.3 个空间问题，最终通过率 92–100%。**题目太简单，测不出系统的短板** |
| BlenderWorld（223 个任务） | 前沿模型的瓶颈在**大场景、细粒度的空间一致性**；GPT-6 Astra 只有 79.9 分 |
| 你的毕设、LL3M 原论文 | 链路最后都有"**用户继续编辑**"这一环 |
| 真实用法 | 搭游戏场景不会一句话说完，而是"先搭村庄 → 加一口井 → 屋顶改红 → 加小路 → 去掉栅栏……" |

现在的 BlendHarness 只接受一条需求：修改轮修的是 Critic 发现的问题，不是用户的新需求；修改模板、Critic、Verifier 都只认最初那一条 `prompt`。

## 2. 目标与非目标

**目标**
1. **会话模式**：一次会话由多轮用户需求组成；从第 2 轮起，在当前场景上修改，而不是重新生成。
2. **不改坏已有的部分**：这一轮没提到的东西保持不变，早期的要求在后面的轮次里依然成立。
3. **上下文与记忆**：轮次增加时，上下文的大小可控，同时不忘记早期的要求，也能理解"那个桶""刚才加的树"这类指代。
4. **两层测评**：程序检查硬约束（完成度、回归、保持率），LLM 裁判评**效果**（好不好、像不像、协不协调），裁判本身要经过人工校准。

**非目标（这一版不做）**：图形界面、撤销 / 重做的交互、多人协作、训练。

## 3. 用户场景示例

```
第 1 轮  在 10 m × 10 m 的草地上搭一个低多边形小村庄：一座小屋（墙、斜屋顶、门、两扇窗）、一口石井、两棵树。
第 2 轮  在小屋东边约 3 米处加一个木头栅栏围起来的小菜园，里面有三排菜。
第 3 轮  把小屋的屋顶改成红色瓦片。
第 4 轮  加一条从小屋门口通到石井的碎石小路。
第 5 轮  再加三棵树，种在村庄北边，不要挡住小路。
第 6 轮  去掉菜园的栅栏，菜保留。
第 7 轮  在石井旁边放一个木桶，贴着井的外壁。
第 8 轮  把刚才那个桶换成两个小一点的。
```
到第 8 轮，场景大约有 80–150 个物体，脚本大约 1000–1500 行。第 8 轮的"刚才那个桶"需要指代消解。

## 4. Workflow 怎么改

### 4.1 现在的流程（一次建模，一条需求）

```
run_build(prompt)
  └─ _Build
       round0:     Coder.run(prompt) → 渲染 → Critic(prompt)            → 存档 round0
       revise(k):  Coder.run(refine(prompt, issues)) → 渲染 → diff → Verifier → 存档 round{k}
       learn → finalize
```

### 4.2 改造后的流程：三层循环

```
run_session(turns)                                  ← 第 1 层：会话（新增，workflow/session.py）
  for 每一轮用户需求 k:
     ┌─ plan_turn       ① 更新需求账本 ② 指代消解 ③ 生成本轮任务说明             （新）
     ├─ edit            Coder 在当前脚本上修改，结束时声明"本轮改了哪些物体"      ← 第 2 层：轮内闭环（复用 _Build）
     ├─ review          渲染 → Critic（本轮需求 + 账本 + 场景登记表）
     ├─ revise(1..N)    没通过 → Coder 修改 → 场景差异 + 回归报告 → Verifier
     ├─ close_turn      轮末快照 → 回归报告 → 更新场景登记表和轮次日志           （新）
     └─ 存档 t{k}_done
         每一次 Coder.run() 内部：现有的 agent loop + rails + 上下文引擎        ← 第 3 层：agent loop（不改）
  finalize_session → session.json（每轮的记录、成本、上下文长度）
```

**关键决定：每一轮内部复用现有的 `_Build`，而不是另写一套。** 具体做法是把 `_Build` 的 `round0` 拆成两种入口：
- `round0_new(prompt)`：现在的行为，用于第 1 轮；
- `round0_edit(task)`：在已有的 `current_script` 上修改，用于第 2 轮起。

`revise`、Critic、Verifier、存档的逻辑全部复用。这样**单轮建模就是"只有一轮的会话"**，原来的测评和实验都不受影响。

### 4.3 每一轮的阶段

| 阶段 | 做什么 | 谁来做 | 成本 |
|---|---|---|---|
| **plan_turn** | ① 账本管理员：输入旧账本和新需求，输出新增、取代、不变的条目；② 指代消解：把"那个桶""刚才加的树"解析成具体的物体名（查场景登记表和轮次日志）；③ 拼出本轮任务说明 | 一次 Haiku 调用，输出 JSON；之后用程序检查（见 5.4） | 约 $0.002 |
| **edit** | Coder 修改脚本；结束前**必须调用 `declare_changes(added, modified, removed, reason)`** 声明本轮改了什么 | Coder（Sonnet） | 主要成本 |
| **review** | 渲染 4 个视角 → Critic 对照"本轮需求 + 账本"挑问题 | Critic（Haiku） | 很低 |
| **revise** | 和现在一样，另外多一份**回归报告**：Coder 声明之外、却发生了变化的物体 | Coder + Verifier | 视情况 |
| **close_turn** | 轮末快照 → 计算本轮的场景差异 → 更新场景登记表（程序）→ 写一行轮次日志（程序，用模板生成，不调用 LLM）→ 存档 | 程序 | 0 |

**`declare_changes` 为什么重要**：
1. **交互使用时没有标准答案**（测评里才有 `touches`），只能拿 Coder 的声明和实际的场景差异做比较："声明之外的变化"就是可疑的回归，交给 Verifier 判断；
2. 场景登记表需要知道"哪个物体是为了哪条需求加的"；
3. 测评时，"声明"和"实际差异"的一致率本身就是一个过程指标：Coder 是否清楚自己改了什么。

| 文件 | 改动 |

### 4.5 存档、分叉和接口

- 每一轮结束存档 `t{k}_done`，轮内修改轮存档 `t{k}_round{r}`；从任意一轮之后分叉：`fork_from=(run_dir, "t04_done")`；
- 做策略对比时，所有策略**从同一个第 1 轮结果分叉**，起点完全相同，第 1 轮也只花一次钱。

**需求是逐轮输入的，系统看不到后面的轮次。**
- 交互模式：真人看完上一轮的结果，再输入下一轮；
- 测评模式：`run_session` 手里有整个会话文件，但**严格按顺序**，每次只把第 k 轮需求的**字符串**交给系统，等这一轮完全结束（含修改轮和存档）再交下一轮。会话文件里的 `expect`、`touches`、`persist`、`requires`、细则清单**只有测评脚本和离线裁判能看到**；
- **用测试保证不偷看未来**：断言第 k 轮所有 LLM 请求的内容里，不出现第 k+1 轮及之后的需求原文，也不出现任何检查项。

```python
run_session(turns, cfg: SessionConfig, run_dir, resume=False, fork_from=None) -> dict   # 测评用
s = Session.start(first_request, cfg, run_dir); s.turn("把屋顶改成红色"); s.fork("t03_done").turn("改成蓝色")
```
`SessionConfig` = `BuildConfig` + `memory: "history" | "structured" | "structured+retrieval"`（对应 M0 / M2 / M3）。

## 5. 上下文与记忆管理（核心）

### 5.1 问题：到底是什么在膨胀

| 会膨胀的东西 | 第 1 轮 | 第 8 轮（估计） | 现在怎么处理 |
|---|---|---|---|
| 用户需求的原文 | 1 条 | 8 条，约 1–2k token | 只有一条 |
| **脚本** | 200–300 行，约 3–5k token（新基线实测） | 1000–1500 行，约 **20–35k token** | 整份常驻在上下文末尾 |
| 场景 | 20–40 个物体 | 80–150 个物体，`inspect_scene` 约 8–15k token | 按需调用 |
| 轮内的工具调用历史 | 每轮新开一次 `coder.run()`，自然清零 | 同左 | 上下文引擎：压缩旧脚本、常驻当前脚本、预算守卫 |
| 评审意见 | 每轮最多 3 条 | 需要知道"早期哪些问题已经接受过" | 只在一次建模内传递 |

**结论**：多轮时，真正的压力**不在对话历史，而在脚本和场景本身**。很多"多轮记忆"方案只做了"对话摘要"，这里不够用。

### 5.2 三个要解决的子问题

1. **记住用户要什么**：早期的要求不能丢，被推翻的旧要求不能再执行（屋顶从棕色改成红色之后，就不能再按"棕色"检查）；
2. **知道场景里有什么**：哪个物体是什么、为了哪条需求加的、由脚本的哪个函数生成，用于指代消解和局部修改；
3. **只看需要看的代码**：脚本很长时，Coder 不需要每一轮都看到全部 1500 行。

### 5.3 分层记忆：六层，按"变化快慢"排列

| 层 | 内容 | 类型 | 怎么写入 | 谁读 | 预算 |
|---|---|---|---|---|---|
| **L0 规则** | 系统提示词 + 修改规则 | 静态 | — | Coder、Critic | 约 1.5k |
| **L1 需求账本** | 有效需求的结构化列表，带来源轮次和状态（有效 / 已取代） | **语义记忆** | plan_turn，账本管理员（Haiku）+ 程序检查 | Coder、Critic、裁判 | ≤ 1.5k |
| **L2 场景登记表** | 物体分组（"小屋：墙、屋顶、门……"）→ 对应哪条需求 → 由哪个函数生成 → 位置和尺寸摘要 | **世界状态** | close_turn，**程序从快照生成** + Coder 的声明 | Coder、指代消解 | ≤ 3k |
| **L3 轮次日志** | 每轮一行："第 7 轮：加木桶 → 新增 Well_Bucket，Critic 通过，无回归" | **情景记忆** | close_turn，**程序按模板生成** | Coder、指代消解 | ≤ 1k |
| **L4 当前脚本** | 小于阈值（约 12k token）时整份常驻；超过阈值后，常驻**大纲**（函数列表 + 文档字符串 + 行号范围），具体代码用 `view_section(name)` 按需加载 | 工作区 | 每次执行成功后更新（已有） | Coder | 全文 ≤ 12k，否则大纲 ≤ 3k + 按需 |
| **L5 轮内工作记忆** | 本轮的工具调用历史 | 短期记忆 | agent loop（已有） | Coder | 上下文引擎 + 预算守卫（已有） |

**排列顺序就是 prompt 的顺序**：L0（不变）→ L1（偶尔变）→ L2/L3（每轮追加）→ 本轮任务 → L4（每步都可能变）→ L5。越稳定的越靠前，**prompt 缓存的命中率越高**。L1 在中间变化时，后面的内容都会失效，所以 L1 采用"只追加、用状态标记取代"的方式更新，尽量不改写已有条目。

**为什么 L2、L3 由程序生成，不用 LLM 写摘要**：LLM 写的摘要可能**编造**场景里没有的东西，而且一旦写错，之后每一轮都会被错误的记忆误导。场景快照才是真实情况，所以登记表**每一轮都从快照重新生成**，而不是在旧记录上累积修改。

**脚本的结构约束（L4 的前提）**：修改规则要求脚本按部件组织成函数（`build_house()`、`build_well()`……），最后由一个 `build_scene()` 调用。这样：
- 大纲有意义，可以按需加载某个函数的代码；
- 场景登记表能把物体对应到函数；
- 局部修改的范围更容易控制，回归更少。

### 5.4 写入时的防护：账本不能"悄悄丢东西"

账本管理员每次输出后，用程序检查：
1. 旧账本里的每一条有效条目，**要么保留，要么被明确标记为"已取代"并给出理由**，不能凭空消失；
2. 新增的条目必须能在本轮需求原文里找到依据；
3. 指代消解的结果，必须是场景登记表里**真实存在的物体名**。

任何一条不满足，就重试一次；还不满足，就退回"把新需求原文直接追加到账本"，保证不丢信息。测评里有标准账本，可以直接算出账本更新的准确率。

### 5.5 指代消解

"刚才那个桶""北边的树""那条小路"——在 plan_turn 里解析：
- 输入：本轮需求 + L2 场景登记表 + L3 轮次日志；
- 输出：本轮任务说明里写明具体的物体名，例如"把 `Well_Bucket` 替换为两个更小的桶，保持贴着井的外壁"；
- 如果有歧义（比如有两个桶），在任务说明里列出候选，让 Coder 用 `inspect_scene` 确认，不让账本管理员瞎猜。

### 5.6 每个角色看到什么

| 角色 | 看到的内容 |
|---|---|
| Coder | L0 + L1 + L2 + L3 + 本轮任务说明（含指代消解结果）+ L4 + L5 |
| Critic | 本轮需求 + L1 账本 + 渲染图 + 场景摘要；规则："重点检查本轮需求；早期的要求只检查有没有被破坏；不要因为早期已经接受的风格而拒绝" |
| Verifier | 本轮要修的问题 + 修改前后的渲染图 + 场景差异 + **回归报告** |
| 裁判（离线） | 见 6.2 |

### 5.7 对照实验：端到端只比 3 组，组件各自用指标测

所有策略**从同一个第 1 轮结果分叉**：

| 策略 | 内容 | 重复次数 |
|---|---|---|
| **M0 完整历史** | 所有需求原文 + 整份脚本 | 2 |
| **M2 结构化记忆** | L1 账本 + L2 场景登记表 + L3 轮次日志 + 整份脚本 | 2 |
| **M3 结构化记忆 + 检索** | M2 + L4 脚本大纲 + 按需检索代码段 | **1** |

**两个主要问题，各对应一组对比**：
1. **M0 vs M2**：结构化记忆能不能减少回归、更好地保持早期需求？这是主要结论，需要足够的样本，所以跑 2 次；
2. **M2 vs M3**：用检索代替整份脚本，能不能在**质量不明显下降**的前提下省上下文和成本？它要回答的是"省了多少、有没有明显变差"，对样本量的要求更低，所以只跑 1 次。

**不为每个组件单独设消融组**，而是用组件自己的指标来测：

| 组件 | 指标 | 标准答案从哪来 | 成本 |
|---|---|---|---|
| 需求账本 | 账本更新准确率（有没有漏条目、取代得对不对） | 会话文件里的标准账本 | 0 |
| 指代消解 | 解析准确率 | 会话文件里的 `refs` | 0 |
| 代码检索 | recall@k；关键词 / 向量 / 混合三种方式的对比 | Coder 实际修改的函数 | **0：在 M2 的轨迹上离线重放** |

**检索可以离线测**：M2 的每一轮都有完整的记录（本轮任务 + Coder 实际改了哪些函数），把检索器在这些记录上重放一遍，就能算出 recall@k，不需要再跑任何建模。所以 M3 这一组只负责回答端到端的问题。

原来的"只有账本"一组（M1）去掉了：它想回答的"账本有没有用"，由账本更新准确率和 M0 vs M2 的对比共同回答。

每种策略都记录：回归率、需求保持率、每轮上下文 token 数、缓存命中率、成本。

### 5.8 面试时可能被追问的问题

| 追问 | 回答要点 |
|---|---|
| 为什么不直接把历史对话做摘要？ | 摘要可能编造、会累积误差；而且多轮时真正大的不是对话，是脚本和场景。所以按"用户意图 / 世界状态 / 事件 / 代码"分层，后两者由程序从真实快照生成 |
| 为什么不对历史做 RAG 检索？ | 需求账本是**全部都要遵守**的约束，不是"找几条相关的"；漏检一条就是一次需求违背。所以账本全部放进上下文，检索只用在代码按需加载、指代消解、标出相关需求这三处（5.9） |
| 检索效果怎么评估？ | 用 Coder 实际修改的函数当标准答案，算 recall@k，不需要人工标注；再对比关键词、向量、混合三种检索 |
| 为什么用 SQLite + numpy，不用向量数据库？ | 一个会话只有几百条，暴力计算就够快；和存档放在一起，分叉时整份复制，状态一致。规模变大再换 |
| 怎么防止遗忘？ | 账本只追加、用状态标记取代；写入时有程序检查；测评里用"需求保持率"直接测量 |
| 被推翻的需求怎么处理？ | 账本条目有"已取代"状态并指向新条目，Critic 和裁判都只检查有效条目 |
| 上下文压缩和 prompt 缓存怎么权衡？ | 按变化快慢排列各层；账本只追加；现有的上下文引擎也是"每块内容只在过期时压缩一次"，减少缓存失效 |
| 怎么证明记忆方案有效？ | 端到端只比两组：M0 vs M2（记忆）、M2 vs M3（检索），同一个起点分叉，按会话配对 + bootstrap；各组件用自己的指标测（账本准确率、指代消解准确率、检索 recall@k），这样能定位是哪个组件起作用，又不用为每个组件都跑一组昂贵的实验 |


### 5.9 M3 的检索：切分、三种检索、存储、测评（已实现）

**脚本怎么切**（`memory/session/sections.py`）：实测 Sonnet 并不会"每个部件一个函数"，而是写几个辅助函数（`box()`、`mat()`），再在顶层用注释分段（`# ---- stone well ----`）平铺调用。所以一个代码段是：
- 顶层的 `def` / `class`（类型 helper，用函数名命名）；或
- 一段顶层代码（类型 block），从"空行后的注释"开始，用注释命名；没有注释就用它创建的物体的主要分组命名。

每段记录它创建的物体名（用 `ast` 取每个调用的第一个字符串参数），这样场景登记表里的物体可以对应回代码段；还记录它**定义**和**读取**的变量名（`M_SHINGLE = material(...)` 定义 `M_SHINGLE`，屋顶段读取它）。一个细节：`# --- materials ---` 常写在 `def material()` 上面，紧跟的 `M_* = material(...)` 段没有自己的注释，就沿用这个横幅名。

**Coder 看到什么**：`script_view="outline"` 时，固定在上下文末尾的不再是整份脚本，而是**大纲**（每段一行：名字、行号、物体）加上**检索到的 k 段原文**（默认 k=3）。其余代码段用新工具 `view_section(name)` 按需加载。每次都从当前脚本重新切分，所以不会看到过期的代码。

**三种检索**（`memory/session/retrieval.py`）：
- BM25：标识符按 `_`、`.`、驼峰拆开（`WellBucket_2` → well, bucket），对物体名这种精确词很准；
- 向量：本地 `BAAI/bge-small-en-v1.5`（fastembed，384 维，CPU），能处理换说法（"小房子" → cottage）。中转站暂时没有 embedding 通道；本地模型免费、结果确定，离线重放可复现；
- 混合：RRF（score = Σ 1/(60 + rank)），只融合名次，不用校准两种分数；BM25 得分为 0 的段不参与投票。

查询 = 本轮需求 + 账本管理员解析出的指代物体名（"the little house" → `Cottage_Walls`…）+ 这些物体用的材质名（来自上一轮的场景快照），所以指代消解也直接帮了 BM25。

**按定义扩展**（`with_definitions`）：检索出前 k 段后，再补最多 2 个"定义了这些段所读取变量"的代码段。原因来自真实冒烟：用户说"把屋顶改红"，真正要改的是材质段里的 `M_SHINGLE = material("Shingle", ...)`，但屋顶段只是**引用**了 `M_SHINGLE`；三种检索都排不到材质段，Coder 多花了 4 次读取才找到。按 def-use 关系补上定义段，是利用代码结构、而不只靠文本相似度的检索。

**存储**：向量按（模型, 文本哈希）缓存在会话的 `memory.db`（`embeddings` 表）里：没变的代码段不会重复计算，分叉时随记忆一起复制。一个会话只有几百段，用 numpy 暴力算余弦就够，不需要向量数据库。

**标准答案和测评**：每一轮（不论哪种策略）都记录 `touched_sections`：修改前脚本里**被这轮改到的代码段**，按行 diff 计算（删除、替换的行归属所在段，插入归属插入点所在段），所以改了注释名也能对上。**新加的整段代码不算**（插入的内容以"空行 + 注释"开头，自成一段）：检索的目的是给出要修改的旧代码，新代码不需要检索（冒烟里"加一个地上的桶"被误算成改了上一段，修正后去掉）。M3 的会话还会当场记录 recall（只看前 k 段，以及加上定义扩展后）。`eval/replay_retrieval.py` 在任意会话的轨迹上重放 bm25 / vector / hybrid，以及各自 +deps，输出 recall@1/3/5，不调用任何模型；注意 +deps 实际展示 k+2 段，比较时要按展示的段数对齐。

**冒烟结果（2 个不同的编辑，只验证机制，不是结论）**：修正前 hybrid recall@3 = 0.5（材质段被误命名、查询里没有材质名）；修正段命名并在查询里加材质名后 recall@3 = 1.0；recall@1 只有 0.25，加定义扩展（1 + 2 段）后 = 1.0。M3 的真实一轮（从 M2 会话第 1 轮分叉）：通过、0 个非请求改动、$0.28。

## 6. 测评：三层

### 6.0 先看一个例子：程序检查到底在做什么

程序检查是一把**自动阅卷的尺子**：每一轮结束后，自动判断两件事——**这一轮要求的事做到了没有**、**有没有顺手把别的东西改坏**。它本身不做统计，等会话跑起来以后，用它给每一轮打分，再汇总成指标。

**例子**：村庄会话的第 6 轮，用户说"在石井旁边放一个木桶，贴着井的外壁"。

**程序看到的不是图片，而是物体清单**（场景检查器的输出）：每个物体的名字、占据的空间范围（包围盒）和材质颜色。
```
Cottage_Walls   x -1..1    y -1..1    z 0..2
Cottage_Roof    ……         颜色：红
Well_Ring       x 3..4     y -3..-2   z 0..0.8
Well_Bucket     x 4.0..4.3 y -2.6..-2.3 z 0..0.35
……
```

**出题时预先写好的标准答案**（在 `eval/sessions_draft.json` 里，易读版见 `docs/sessions_draft.md`）：

| 检查 | 意思 | 程序怎么判断 |
|---|---|---|
| 存在 `bucket\|barrel\|pail` | 有没有桶 | 物体名里有没有这些词 |
| 贴近 `bucket` 和 `well`，间隙 ≤ 5 cm | 桶是不是贴着井 | 两个物体范围之间的距离 |
| 着地 `bucket` | 桶是不是放在地上 | 桶的最低点是不是在地面附近 |
| 只允许改动 `bucket\|barrel\|pail` | 别的东西不能动 | 对比这一轮前后的物体清单 |

**程序的输出**：
```
存在：通过    贴近：通过（间隙 0.000 m）    着地：通过（最低点 z = 0.000）
回归：无（其他 87 个物体都没变）  →  这一轮完成
```
如果系统顺手把一棵树挪了位置，就会报出"Tree_3 被移动了 → 回归"。

**"数几个"要数实例，不是数物体**：一个床头柜通常由十几个零件组成（`Nightstand_L_Body`、`Nightstand_L_Top`、`Nightstand_L_Drawer_1`……）。直接数"名字里带 nightstand 的物体"，一个床头柜就能数出 14 个，"至少 2 个"永远通过，这条检查就没有意义了。所以先把零件归到同一个实例再数：名字里的方位词（L / R / Left / Front……）或第一个数字相同的零件属于同一个；互相接触的零件也属于同一个。在 4 个真实的历史场景上验证过：窗户、树、床头柜、台灯都数对了。

**最后汇总成的指标**（见 6.4）：

| 指标 | 来自 | 意思 |
|---|---|---|
| 单轮完成率 | 每轮的检查是否全部通过 | 用户要求的事做到了多少 |
| 回归率 | 每轮不允许改的物体有没有被改 | 改坏了多少不该动的东西 |
| 需求保持率 | 最后一轮再检查一遍标了"要一直成立"的条目 | 早期的要求后来还记不记得 |

**三步的关系**：第 1 步是**造尺子**（程序检查器 + 题目），第 2 步是**造要被量的东西**（多轮会话），之后才开始**量和比较**（M0 / M2 / M3）。

### 6.1 第一层：程序检查（硬约束）

每一轮写好期望的变化，基于场景快照检查，纯 Python：

| 检查 | 含义 |
|---|---|
| `exists` / `absent` / `count` | 名字匹配某个模式的物体存在 / 不存在 / 数量在范围内 |
| `near` / `on` / `direction` | 间隙、上下关系、方位（+x 为东，+y 为北） |
| `grounded` | 最低点在地面上 |
| `above` | A 整体在 B 的上方，水平方向有重叠（画在床头上方） |
| `contains_xy` | A 的水平范围包住 B（地毯在床下面并露出两边） |
| `evenly_spaced` | 一组物体沿某个轴等距，间距的变化在容差以内 |
| `material_hue` | 材质的基础颜色落在某个色相范围 |
| `touches` | 本轮**允许**改动的物体名模式；其余物体的变化都算回归 |
| `persist` | 之后一直要成立的检查，用来测需求保持率 |
| `requires` | 这一轮依赖前面哪些检查（例：第 6 轮"去掉菜园的栅栏"依赖第 2 轮的"菜园存在"）。前置没满足时，这一轮**照常执行**，但记为"前置失败"，单独统计，不计入完成率 |

名字用宽松的模式匹配（审计显示 3664 个物体都有有意义的名字）；匹配不上的记为"无法判定"，单独统计。

### 6.2 第二层：LLM-as-judge（效果）

程序检查只能回答"有没有、在不在、颜色对不对"，回答不了"**好不好看、像不像、整体协不协调、改得是否克制**"。这一层用 LLM 裁判来评。下面的设计参考了几种业界常用的做法：

| 做法 | 出处 | 核心思路 | 这里借鉴什么 |
|---|---|---|---|
| **问题分解（QG/A）+ 依赖图** | DSG（ICLR 2024，Google）、TIFA | 把需求拆成**原子问题**（实体、属性、关系各一个），组织成依赖图；父问题答"否"，子问题就不再问，避免自相矛盾的回答 | 本轮细则清单的结构，以及"前置失败"的处理 |
| **两两比较 + Elo** | GPTEval3D（CVPR 2024） | 让多模态模型比较两个 3D 结果，按多个维度各选一个更好的，再换算成 Elo；对输入做扰动、多次取平均来降噪 | 策略对比的方式和维度 |
| **二元细则 + 整体打分** | BlenderWorld（223 个任务、2651 条细则） | 每个任务写很多条"是 / 否"细则，再加一个整体质量分，两者融合 | 细则和打分两条线并行 |
| **人类偏好的 Elo** | 3DCodeArena、LMArena | 人做两两比较，Bradley–Terry 拟合，bootstrap 置信区间 | 人工校准的形式 |
| **裁判的偏差** | MT-Bench（LLM-as-a-judge） | 位置偏好、偏爱更长的回答、偏爱自己家族的模型 | 交换顺序、换不同家族的裁判 |
| **先推理再打分、带锚点的量表** | G-Eval、Prometheus | 每个分数都配有具体的描述，先写理由再给分 | 维度打分的写法 |

#### ① 本轮细则清单（每轮，原子问题 + 依赖）

出题时，把每一轮的需求拆成**原子问题**（每个问题只问一件事），并标出依赖关系：

```
本轮需求：在石井旁边放一个木桶，贴着井的外壁。
Q1  场景里有木桶吗？                             [实体]
Q2  木桶是木头材质的吗？                ← 依赖 Q1   [属性]
Q3  木桶贴着石井的外壁吗？              ← 依赖 Q1   [空间关系]
Q4  木桶立在地面上（没有悬空、没有插进井里）吗？ ← 依赖 Q1 [物理合理性]
Q5  木桶相对石井的大小合理吗？          ← 依赖 Q1   [比例]
P1  小屋、小路、菜园的位置和样子和上一轮一样吗？      [保持：上一轮之前的有效需求]
```
- **Q1 答"否"时，Q2–Q5 不再问，直接记为"否"**，避免出现"没有木桶，但木桶是木头的"这种矛盾回答（DSG 的做法）；
- 问题在**出题时就写好**，和程序检查的 `expect` 放在一起，不让裁判自己出题。出题可以先用 LLM 生成草稿，再人工审核；
- 程序能检查的问题（比如 Q1、Q4），同时用程序判一遍，**用来测裁判在有标准答案的问题上的准确率**；
- 指标：**细则通过率**，按问题类型（实体 / 属性 / 空间关系 / 物理合理性 / 比例 / 保持）分别统计。

#### ② 维度打分（每轮，1–5 分，带锚点）

以 GPTEval3D 的五个维度为基础，针对多轮编辑做了调整：

| 维度 | 对应 GPTEval3D | 1 分 | 3 分 | 5 分 |
|---|---|---|---|---|
| **本轮需求完成度** | 文本-资产对齐 | 没做或做错 | 做了，但有明显偏差 | 完全按要求做到 |
| **早期需求保持** | （多轮新增） | 多处早期要求被破坏 | 有一处被破坏 | 全部保持 |
| **修改克制度**（对比修改前后） | （多轮新增） | 大面积重做 | 改了一些不该改的 | 只改了要求的部分 |
| **空间与物理合理性** | 3D 合理性 | 多处悬空、穿插、比例失调 | 有一处明显问题 | 没有明显问题 |
| **几何细节** | 几何细节 | 像占位的方块和圆柱 | 能认出来，细节一般 | 形状有辨识度、细节到位 |
| **材质与整体协调** | 纹理细节 + 纹理-几何一致性 | 材质、风格与场景明显冲突 | 有些不协调 | 新加的部分和已有场景融为一体 |

- 输入：本轮需求、有效的账本、**修改前和修改后**各 4 张渲染图、本轮场景差异的摘要；
- 输出：每个维度**先写一两句依据，再给分**；
- 不设"总分"，各维度分别报告。合成一个总分会掩盖问题，比如"完成度很高但改坏了别的"。

#### ③ 两两比较（策略对比时用，GPTEval3D 的做法）

- 同一会话、同一轮，两种策略（比如 M0 和 M2）的结果并排给裁判，按上面 6 个维度**各选一个更好的**（A / B / 差不多）；
- **每一对都交换左右顺序再问一次**，两次不一致就记为"差不多"；
- 用 Bradley–Terry 拟合出各策略在每个维度上的 Elo，bootstrap 求置信区间。

#### 裁判本身的可靠性（必须做，否则分数不可信）

| 措施 | 针对什么 |
|---|---|
| **裁判用 GPT 或 Gemini**，和 Coder（Sonnet）、Critic（Haiku）不是同一家族 | 偏爱同族模型的输出 |
| 裁判和 Critic 分开，裁判的意见**永远不反馈给系统** | 系统迎合裁判（古德哈特定律） |
| 两两比较时交换顺序 | 位置偏好 |
| 每个样本评 3 次，报告标准差；波动大的维度降权或删除 | 打分不稳定 |
| 在程序能判断的细则上核对裁判的准确率 | 看图看错 |
| **人工校准**：抽 40–60 个样本，用校准页面让你独立标注，细则用 Cohen's κ、打分用 Spearman 相关；**一致率不够的维度不作为结论** | 裁判和人的判断不一致 |
| 报告里写明裁判模型、提示词版本、和人工的一致率 | 可复现 |

**成本**：每次调用约 8 张图 + 文本，约 $0.02–0.04；细则 + 打分各 3 次约 $0.15 一轮。一个 6 轮会话约 $1；3 个会话 × 3 种策略的试点约 $9。

### 6.3 第三层：人工

- 用于校准裁判（见上）；
- 每种策略抽几个完整会话，看最后一轮的渲染图，作为定性的案例。面试时可以展示"同一个会话，M0 和 M2 第 6 轮的结果对比"。

| 指标 | 层 | 用途 |
|---|---|---|
| **回归率** | 程序 | **主要指标之一** |
| **需求保持率** | 程序 | **主要指标之一** |
| 单轮完成率 | 程序 | 次要 |
| 本轮细则通过率 | 裁判 ① | 次要：程序测不到的语义完成度 |

### 6.5 实验计划

**主实验用固定脚本 + 前置条件**：所有策略面对完全相同的需求，配对比较才公平。

**试点（约 $30）**：3 个会话 × 6 轮 × M0、M2、M3 × 1 次，从同一个第 1 轮分叉，再加裁判评分。要回答：
- 程序检查的无法判定率够不够低？
- 回归率大概多少？各策略之间有没有差距的迹象？
- 检索 recall@k 大概多少（在 M2 的轨迹上离线重放）？M3 里检索漏掉代码时，会不会导致回归？
- 裁判的重复评分稳不稳定？

**正式实验（约 $65–75）**：8 个会话 × 6 轮 × （M0 × 2 次 + M2 × 2 次 + M3 × 1 次）= 240 轮；人工校准裁判；**预先注册**主要指标（回归率、需求保持率）和判定规则，按会话配对 + bootstrap。

**补充实验：模拟用户（定性，约 $15）**：真实用户会根据上一轮的结果决定下一步，比如"菜园再往东挪一点"，固定脚本做不到这一点。补充实验用一个 LLM 扮演用户：给它目标场景的描述和每一轮的渲染图，让它决定下一轮说什么，包括纠正。和 τ-bench 的用户模拟器思路相同。这组实验**不可复现**（不同策略看到的需求不一样），所以只做定性观察，不作为主要结论。这个模拟用户以后可以复用到个人助手和多轮 RL 上。

### 检索专题（retrieval.py）

下面所有数字，都是在真实村庄脚本（切成 16 段）上，用查询 **"Make the cottage roof red, like clay tiles."** 实际跑出来的。

#### 1. BM25 详解

**第一步，切词。** 查询变成：`cottage, roof, red, like, clay, tile`。make、the 是停用词，被去掉了；tiles 去掉复数变成 tile。

**第二步，算每个词有多"值钱"（IDF，逆文档频率）：**

| 词 | 在几段里出现 | IDF |
|---|---|---|
| clay | 1 / 16 | **2.43** |
| tile | 1 / 16 | **2.43** |
| cottage | 2 / 16 | 1.92 |
| red | 2 / 16 | 1.92 |
| roof | 4 / 16 | 1.33 |
| like | 0 / 16 | 不计分 |

`IDF = log(1 + (总段数 − 含该词段数 + 0.5) / (含该词段数 + 0.5))`。越稀有的词，命中一次越说明"就是这段"。

**第三步，每段的得分 = 对每个查询词求和：IDF × 词频部分 ÷ 长度部分。**
```
每个词的贡献 = IDF × f×(k1+1) / (f + k1×(1 − b + b×段长/平均段长))
```
- `f`：这个词在这段出现的次数；
- `k1 = 1.2` 控制**词频饱和**：出现 8 次不会比出现 2 次多拿 4 倍分，而是越往后加得越少；
- `b = 0.75` 控制**长度惩罚**：段越长扣得越多，平均段长是 39 个词。

**结果：**

| 段 | 分数 | 段长 | 命中的词（次数） |
|---|---|---|---|
| **materials** | **10.11** | 87 | roof 8, red 5, clay 2, tile 2 |
| cottage | 8.58 | 23 | cottage 7, roof 5, red 1 |
| door | 3.19 | 15 | cottage 2 |
| stone well | 2.17 | 62 | roof 5 |

materials 排第一，因为材质名 `RoofClayRed`、`RoofTiles` 拆开后正好包含 roof、clay、red、tile，而 clay 和 tile 都是最稀有的词。materials 段很长（87 个词，是平均长度的两倍多），被扣了一些分，但仍然领先。

**一句话总结**：BM25 = 稀有词加权 + 词频有上限 + 长段扣分。它不懂词的意思，只做精确的字面匹配。

#### 2. BM25 为什么这么设计（它和正则匹配有什么不同）

**正则 / grep 是"布尔匹配"**：每段只有"匹配"和"不匹配"两种结果，没有先后顺序。这在**你确切知道要找什么**时最好用，比如 `grep "Well_Roof"`，项目里的程序检查（`expectations.py`）就是用正则匹配物体名。但检索面对的是一句**自然语言**，问题就来了：

| 做法 | 在例子上的结果 | 问题 |
|---|---|---|
| 所有词都要出现（AND） | **0 段**匹配 | 用户的话里总有代码里没有的词（like），一个都找不到 |
| 任一词出现即可（OR） | **5 段**匹配：gable_roof、materials、cottage、door、stone well | 匹配到了，但**没有先后**，不知道该给 Coder 哪 3 段 |

所以检索需要的不是"匹不匹配"，而是"**有多相关**"，也就是一个**分数**，用来排序。BM25 的每个部分，都是为了修正"直接数命中次数"的一个毛病。这也是信息检索几十年演化的路线：布尔匹配 → TF（数次数）→ TF-IDF → BM25。

1. **为什么要 IDF（稀有词加权）？** 直接数次数的话，stone well 段里 roof 出现 5 次，得 5 分；一段只含 clay、tile 各 1 次的代码只得 2 分。可是 roof 在 4 段里都有，几乎每个带屋顶的东西都提到它；clay、tile 全脚本只有一段有，命中它们几乎就能确定是这段。IDF 让稀有词更值钱：clay 的 2.43 是 roof 1.33 的近两倍。
2. **为什么词频要饱和（k1）？** 一段里 roof 出现 8 次，不代表它比出现 2 次的段"相关 4 倍"，多半只是那段代码重复写了很多次同一个变量。不加限制的话，一个高频词就能把排名霸占。BM25 用 `f×(k1+1)/(f+k1)` 让它越加越慢（k1=1.2 时）：

   | 出现次数 f | 1 | 2 | 5 | 8 | 20 |
   |---|---|---|---|---|---|
   | 词频得分 | 1.00 | 1.38 | 1.77 | 1.91 | 2.08 |

   从 1 次到 2 次加了不少，从 8 次到 20 次几乎不加。也就是说，**出现**比**出现很多次**重要得多。
3. **为什么要长度惩罚（b）？** 长段落天然包含更多词，什么查询都能沾上一点。不惩罚的话，最长的那段永远排在前面。b=0.75 表示按段长和平均段长的比例扣分：materials 有 87 个词，是平均的 2.2 倍，所以被扣了一些分。
4. **为什么 BM25 至今还在用？** 它没有需要训练的东西，算得极快，完全可解释（能说清每一分从哪来），而且对**精确的名字**（物体名、变量名、错误码）比向量检索更准。所以 Elasticsearch 默认用它，现在的 RAG 系统也几乎都是"BM25 + 向量"混合检索。

**我们在 BM25 前面还加了一步专门的切词**：把 `WellBucket_2` 拆成 well、bucket。正则匹配 "bucket" 时，大小写不同也会匹配失败，更别说拆驼峰了。这一步是专门为"代码里的标识符"设计的。

#### 3. bge-small 模型：在哪，为什么选它

**在哪：**
```
/var/folders/51/fnlnxc19741ck43tfgty1y5c0000gn/T/fastembed_cache/models--Qdrant--bge-small-en-v1.5-onnx-Q/
  ├── model_optimized.onnx    ← 模型本体
  ├── tokenizer.json          ← 分词器
  └── config.json 等
```
- 一共 64 MB，在 macOS 的临时目录（`$TMPDIR`）下。第一次调用时由 `fastembed` 从 HuggingFace 自动下载；
- 如果想放到固定位置，可以在 `.env` 里设置 `FASTEMBED_CACHE_PATH`。

**它是什么：** 北京智源（BAAI）开源的 BGE 系列里最小的英文版本，3300 万参数。Qdrant 把它转成了 **ONNX 格式并做了量化**，这样不需要安装 PyTorch，只用 CPU 就能跑。输入一段文字，输出 384 个数字，并且已经归一化成长度为 1 的向量。

**为什么选它：**
1. **没得选 API**：中转站的 key 没有 embedding 通道（试过的三个模型都返回"no channel"）；
2. **本地运行，免费**：可以无限次重放，不花钱；
3. **结果确定**：同样的输入永远得到同样的向量，离线重放结果可复现。API 模型可能被悄悄升级；
4. **小而快**：64 MB，CPU 上几十毫秒就能算完一批；在 MTEB 检索榜上，同体量的模型里它排得靠前；
5. **够用**：检索的是英文代码和英文需求，场景很窄。

**例子的结果（余弦相似度）：** cottage 0.695 > gable_roof 0.648 > materials 0.645。它把 `gable_roof`（坡屋顶函数）排到了第二。字面上查询里没有 gable，但模型"理解"这个函数和屋顶有关，这正是 BM25 做不到的。

#### 4. VectorCache 是什么

就是一张**向量缓存表**，存在会话的 `memory.db` 里：

```
embeddings 表
model（模型名）           hash（段文本的 sha1 指纹）   dim   vec（二进制，1536 字节）
BAAI/bge-small-en-v1.5    73eeacb74f42...             384   ...
```

**为什么要缓存：** 每一轮都要检索，但每轮通常只改一两段代码。以 16 段为例：
- 第 1 次：16 段全部要算向量；
- 第 2 次：14 段没变，**指纹相同，直接从表里读**，只算改过的 2 段和查询本身。

**设计细节：**
- **用文本指纹做主键，不用段名**：段名相同但内容变了，指纹就变，会自动重算，不会读到旧向量；
- **主键里带模型名**：以后换模型，旧向量不会被误用；
- **跟着记忆一起分叉**：同一个 SQLite 文件，复制一份就全带走了。

#### 5. SQLite 怎么配置

**不需要配置。** 这是 SQLite 和 MySQL 最大的区别：

| | SQLite | MySQL |
|---|---|---|
| 安装 | Python 自带 `import sqlite3` | 要装服务器软件 |
| 启动 | 没有服务，不需要启动 | 后台常驻进程 |
| 连接 | `sqlite3.connect("文件路径")` | 主机 + 端口 + 用户名 + 密码 |
| 建库 | 文件不存在就自动创建 | `CREATE DATABASE` |

代码里一共就这两步：
```python
db = sqlite3.connect("runs/xxx/memory.db")     # 打开，文件不存在就新建
db.execute("CREATE TABLE IF NOT EXISTS embeddings (...)")   # 表不存在就建
```
"数据库服务"其实就是一段直接读写这个文件的 C 代码，跑在我们自己的 Python 进程里。

#### 6. RRF 融合详解

**难点：两种分数没法相加。** BM25 的分数在 0 到 15 之间，余弦相似度在 0.5 到 0.7 之间。直接相加的话，BM25 会完全压倒向量；要做加权，就得调权重，而且换一个场景权重可能又不对了。

**RRF 的做法：扔掉分数，只用名次。**
```
融合分(段) = Σ 每一路的 1 / (60 + 这一路里的名次)
```

**例子：**

| 段 | BM25 名次 | 向量名次 | 计算 | 融合分 |
|---|---|---|---|---|
| **cottage** | 2 | **1** | 1/62 + 1/61 | **0.0325** |
| materials | **1** | 3 | 1/61 + 1/63 | 0.0323 |
| gable_roof | 5 | 2 | 1/65 + 1/62 | 0.0315 |
| door | 3 | 5 | 1/63 + 1/65 | 0.0313 |

**为什么是 60？** 它让名次之间的差距变得平缓：第 1 名 1/61 ≈ 0.0164，第 5 名 1/65 ≈ 0.0154，只差 6%。所以**两路都排得靠前**的段，比**只在一路里排第一**的段更有优势。cottage 两路都在前两名，超过了 BM25 第一、向量第三的 materials。60 是原论文的经验值，Elasticsearch 默认也用 60。

**一个细节**：BM25 里得 0 分的段（和查询一个词都不重合）**不参与 BM25 这一路的投票**。不然这些段会按脚本顺序领到名次分，`imports` 这种毫无关系的段也能白白拿分。

**RRF 的局限（面试可能会被追问）**：它丢掉了"差距有多大"的信息。BM25 里 materials 10.11 分、遥遥领先，到了 RRF 里也只按"第 1 名"计分，所以被 cottage 微弱反超。如果要保留分数差距，可以换成"分数归一化后加权求和"，代价是要调权重。我们的场景里，前 3 名本来就都会展示，这点差异影响不大。

#### 7. 检索最后只返回 top k 吗？

**不只是。** 分四层：

| 函数 | 返回什么 | 谁用 |
|---|---|---|
| `Retriever.rank` | **所有段**的完整排名和分数 | 离线重放：要算 recall@1/3/5，所以需要完整排名 |
| `Retriever.search` | **前 k 段**的名字（默认 k = 3） | session.py |
| `with_definitions` | 前 k 段 **+ 最多 2 个定义段** | session.py |
| Coder 实际看到 | **全部段的大纲** + 上面这至多 5 段的**原文** | Coder |

所以 Coder 并不是"只能看 3 段"：
- **大纲**让它知道全部 16 段各是什么、在第几行、创建了哪些物体；
- **原文**只给最可能要改的那几段；
- 需要其他段时，它自己调用 `view_section("tree 2: pine")` 去取。

这就是"渐进式披露"：先给目录和最相关的内容，其余的按需取用。Claude Code 读文件、技能库只放目录，都是同样的思路。


### Coder 怎么接入 M3（摘要）

- **`script_pin`**（`coder.py`）：上下文末尾固定显示的脚本。非 outline 模式时是整份脚本，和原来一样；outline 模式时是"大纲 + 召回的段的原文"。它是 `lambda`，每一步都从当前脚本重新切分，所以永远不过期。
- **`view_section`**（`blender_tools.py`）：按段名返回原文，可以直接当 `edit_script` 的 `old_string` 用；出错时列出所有段名，方便模型自己纠正。只在 outline 模式下提供，同时改写 `edit_script` 的描述，所以 M0 / M2 / 单次建模的工具列表不变。
- **参数传递**：`script_view` 和 `focus` 从 session → `run_build` → `BuildState` → `BlenderTools`。focus 存进状态，续跑时用同一组段，不重新检索，保证可复现。
- **真实冒烟**：钉住的部分 4,088 个字符，整份脚本 10,123 个字符，少了约 60%。材质段没被召回，Coder 靠大纲找到了它，但多读了 4 次，这促成了"按定义扩展"和"段命名"两处修复。
- **已知局限**：focus 整轮固定，Critic 指出的其他地方的问题只能靠 `view_section` 自己去取。可以改进成修改轮按问题重新检索。

### session.py 整体（摘要）

- **结构**：配置（`SessionConfig`）、状态（`SessionState`）→ 三种策略的任务文字（`turn_texts` 对应 M0，`structured_texts` 对应 M2/M3）→ 辅助函数（`retrieval_query`、`unrequested_changes`）→ `Session`（启动、`turn`、`_plan`、`_query`、`_write_summary`）→ `run_session`。
- **一轮的流程**：恢复记忆 → 账本管理员 → 拼任务（M3 还要检索 + 按定义扩展）→ `run_build` → 算非请求改动和 touched_sections（M3 还要算 recall）→ 写回登记表和日志 → 存两份对齐的存档（`tNN_done.json` 和 `memory_tNN.db`）。
- **三种策略只在"Coder 看到什么"上不同**，其他流程完全一致：M0 是历史原话 + 整份脚本；M2 是账本 + 登记表 + 日志 + 整份脚本；M3 是 M2 的内容 + 大纲 + 召回的段。
- **可靠性**：每轮从上一轮的副本恢复，续跑幂等；分叉时把脚本和记忆一起复制；一次只喂一条需求，系统看不到后面的轮次；续跑时会核对已完成轮次的需求。

**已修复（2026-10-27）**：新物体对应哪条需求。一轮只有一条新需求时，本轮新增的物体都记到这条上；有多条时记为 None，因为无法知道哪个物体对应哪条需求，宁可不记，也不记错。


### 第 5 步：实验运行器和裁判（摘要）

- **`eval/run_sessions.py`**：
  - 每个会话的第 1 轮只跑一次（`base/`），M0 / M2 / M3 都从它分叉，跑第 2–6 轮；
  - 系统只拿到需求原文；expect、touches、persist、rubric 只留在评测这一侧；
  - 每轮用 `expectations.py` 做程序检查，汇总成完成率、回归率、需求保持率、成本、token 数、检索 recall，输出到 `summary.md`；
  - 可以续跑；某一组崩溃了只记录到 crash.json，不影响其他组。
- **`eval/judge.py`**：
  - 三种模式：细则清单（带依赖，取多数票）、6 个维度打分（先写依据再给分，算均值和标准差）、两两比较（交换左右各问一次，两次一致才算赢，用 Bradley–Terry 算 Elo，按会话做 bootstrap）；
  - 裁判看到的早期需求一律用原话，不用各策略自己的账本，避免把策略差异带进评判；
  - 结果缓存在每轮目录的 `judge/` 下，重跑只为新的轮次付费。
- **key 填在哪**：`.env` 里的 `JUDGE_BASE_URL` 和 `JUDGE_API_KEY`。名字以 gpt / gemini 开头的模型会用这组 key；没填的话退回 `OPENAI_*`。
- **embedding 模型**：已移到项目里的 `models/fastembed/`（已加入 gitignore），也可以用 `FASTEMBED_CACHE_PATH` 指定别的位置。

## 12. 试点结果与分析（2026-10-27/28）

> 实验目录 `runs/sessions/pilot_20261027/`，设计见本文前面各节。
> **性质：探索性试点。** 3 个会话，样本小；程序检查是在看过试点数据之后校准的。所以本文的结论都是"观察到的现象 + 查实的原因"，不是事先注册好假设的验证性结果。

### 12.1 一句话结论

- **结构化记忆（M2）在 6 轮的短会话里没有显示出收益**：完成率和 M0 一样，都是 93%，每轮的输入 token 还多了 22%。原因是 6 句短需求的完整历史本来就很短，账本和登记表要解决的"遗忘、指代"问题在这个长度上还没有出现。
- **大纲 + 检索（M3）在这个脚本规模下得不偿失**：完成率 73%，成本多出 50%。从轨迹里查实了两个原因：Coder 因为看不到全文而频繁读代码；有 2 次在看不全的情况下凭记忆整体重写了场景。
- **LLM 裁判的两两比较支持"没有差别"**：6 个维度里有 5 个平局居多，只有几何细节 M0 占优（15:5），原因未查实，样本也小。
- **组件本身是可用的**：账本管理员 45 次调用里 0 次兜底，抽查的 7 次"取代"全部正确；离线重放时，向量检索的 recall@3 是 0.76。M3 的问题出在 **Coder 怎么用检索结果**，不在检索本身。
- **程序检查器必须先用试点校准**：发现 5 处误判，全部是名字匹配和规则定义的问题。

### 12.2 实验设置

| 项目 | 设置 |
|---|---|
| 会话 | village（低多边形村庄）、bedroom（卧室一角）、street_corner（街角），各 6 轮；需求逐轮输入，系统看不到后续轮次 |
| 策略 | M0 历史原话 + 整份脚本 ×2；M2 账本 + 登记表 + 日志 + 整份脚本 ×2；M3 = M2 + 大纲 + 召回的段 ×1 |
| 公平性 | 每个会话的第 1 轮只跑一次，所有组都从它分叉；各策略之间只有 Coder 看到的上下文不同 |
| 模型 | Coder Sonnet 4.6（思考强度 low），Critic / Verifier / 账本管理员 Haiku 4.5，裁判 gpt-5.5（不同家族） |
| 规模 | 3 个第 1 轮 + 15 组 × 5 个编辑轮 = 75 个编辑轮；建模共 $48.6 |

**检索（在 M2 的轨迹上离线重放，不调用模型）**

|---|---|---|---|

- 漏召回的典型例子："把路灯挪到斑马线旁边"召回了斑马线段，而真正要改的是路灯段；还有 Coder 修改了辅助函数（`make_mat`、`make_cyl`），这类段很难从需求文字里检索到。

### 12.4 原因分析

#### 12.4.1 为什么 M2 没有收益

1. **历史太短**：6 轮需求一共只有几百个 token，M0 的"完整历史"已经足够清楚。M2 的账本 + 登记表 + 日志反而更长：每次调用多出约 0.8k–1.9k token（第一次调用的输入：village 8.3k → 10.1k，street_corner 9.2k → 11.1k，bedroom 6.5k → 7.3k）。bedroom 每轮多出的约 4.5 万 token，主要来自**调用次数更多**（每轮 9.6 次，M0 是 7.3 次），而不是记忆本身变长。
2. **题目没有考到记忆的难点**：需求保持率在所有策略下都是 100%，说明没有哪一轮真正考验了"不要忘记早期的要求"；指代也都很直白（"the roof"、"the middle tree"），整份脚本里都能直接找到。
3. **天花板**：Sonnet 在这些编辑上本来就做得很好（完成率 93%），留给记忆策略的提升空间很小。

#### 12.4.2 为什么 M3 更差（逐条有轨迹证据）

1. **读代码的往返**：M3 每轮平均调用 `view_section` / `view_script` 3.8 次，15 轮里有 12 轮都读了；M0 和 M2 一次都不需要。读回来的内容会一直留在上下文里，所以输入 token 反而比 M0 多。
2. **看不全就重写**：有 2 次，Coder 用 `execute_bpy` 凭记忆把整个场景重写了一遍。street_corner 第 2 轮（加公交站）的修改轮里，路面虚线被重复创建了 88 个（`Lane_Dash.036` 之类的重名编号），另有 36 个被移动，路灯部件也被改了，一共 133 个回归物体。这一组成本 $7.35，是其他组的两倍多。
3. **设计偏离**：设计文档原本规定**脚本超过约 1.2 万 token 才切换到大纲**；试点的脚本大约 300 行（约 5k token），本该显示全文。为了测试 M3，这次强制让它始终使用大纲，相当于在它不该被使用的场景下测试了它。

#### 12.4.3 试点里校准的检查器（全部在正式实验之前，按语义修正）

| 检查 | 误判原因 | 修正 |
|---|---|---|
| 画在床头上方 | `frame` 也匹配到了 `Bed_Frame` | 去掉 `frame` |
| 三排蔬菜 | `row` 匹配到了土垄，所有蔬菜都和它接触，被合并成 1 个实例 | 去掉 `row`；"三排"交给裁判 |
| 实例编号 | `Cabbage_0_3` 只取了第一个数字（排号） | 改成取整串数字 |
| 地毯在床下 | 原文是"两侧露出来"，床头靠墙 | `contains_xy` 新增 `sides` 选项 |
| 三个花盆 | 第 6 轮按要求去掉了一棵树 | 新增 `retires` 字段 |

有两项失败保留不改，因为判断它们是真实的：路灯离斑马线 1.7 m（上限 1.5 m）；镜子有 11 cm 藏在床头板后面。

另外两个工程问题：Coder 的预算上限 $0.50 在多轮会话里不够用（已改为 $1.00）；"非请求改动"依赖 Coder 声明得是否细致（有一次只声明了组名，就多出 61 个），所以只能作参考，回归要以程序检查为准。

### 12.5 局限

- 样本小：3 个会话，M3 每个会话只跑了 1 次；
- 检查器是看过试点数据之后校准的；修正都按语义来，但仍然属于事后分析；
- 题目由我自己设计，偏简单，也偏短；
- 裁判（gpt-5.5）还没有和人工标注做过一致性校准；两两比较的平局里，混着"真平局"和"交换顺序后不一致"两种情况，目前没有分开记录。

### 12.6 下一步应该怎么做

1. **重新设计题目，让记忆真正有用武之地**：12 轮以上的会话；回指很早以前内容的需求（"把第 2 轮加的那个东西改成……"）；中途推翻、之后再恢复的要求；带歧义的指代。
2. **修 M3，再按设计的阈值测试**：
   - 大纲模式下禁止整体重写；
   - 脚本改过之后，压缩之前读到的旧代码；
   - 只在脚本超过阈值时使用大纲；
   - 修改轮按 Critic 指出的问题重新检索。
3. **检索改用向量为主**：在这个任务上，混合检索没有超过单独的向量检索。
4. **在扩大实验之前**，先做裁判的人工校准。
