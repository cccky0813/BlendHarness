# 多轮续写建模：设计文档（v1.1）

> 2026-10-26。目的：让 BlendHarness 支持"用户持续提需求、在已有场景上继续修改"，并建立一套**程序检查 + LLM 裁判**两层的多轮测评。
> 状态：**设计已确认主要方向，还没有写代码。**
>
> **v0 → v1**：去掉"每轮重建"策略；重新设计上下文与记忆管理（第 5 节）；新增 LLM-as-judge 效果评测（第 6.2 节）；把 workflow 的改造细化到文件和阶段（第 4 节）。
> **v1.1 → v1.2**：对照实验从 4 组减为 3 组（去掉"只有账本"），组件改用各自的指标测；M3 只跑 1 次（5.7、6.5）。
> **v1 → v1.1**：明确需求是逐轮输入的，系统看不到后面的轮次（4.5）；会话增加前置条件和模拟用户补充实验（6.1、6.5）；参考业界做法重写裁判指标（6.2）；M3 纳入第一版，用 SQLite 加向量检索实现，并设计检索本身的测评（5.9）；第 10 节改为决定记录。

## 1. 为什么做

| 证据 | 说明 |
|---|---|
| 修复后的新基线（RSI 笔记第 7 站） | 单轮、单件家具或小场景上，Sonnet 第 0 轮每次只有 0.2–0.3 个空间问题，最终通过率 92–100%。**题目太简单，测不出系统的短板** |
| BlenderWorld（223 个任务） | 前沿模型的瓶颈在**大场景、细粒度的空间一致性**；GPT-6 Astra 只有 79.9 分 |
| 你的毕设、LL3M 原论文 | 链路最后都有"**用户继续编辑**"这一环 |
| 真实用法 | 搭游戏场景不会一句话说完，而是"先搭村庄 → 加一口井 → 屋顶改红 → 加小路 → 去掉栅栏……" |

现在的 BlendHarness 只接受一条需求：修改轮修的是 Critic 发现的问题，不是用户的新需求；修改模板、Critic、Verifier 都只认最初那一条 `prompt`。

## 2. 目标与非目标

**目标**
1. **会话模式**：一次会话由多轮用户需求组成；从第 2 轮起，在当前场景上修改，而不是重新生成。
2. **不改坏已有的部分**：这一轮没提到的东西保持不变，早期的要求在后面的轮次里依然成立。
3. **上下文与记忆**：轮次增加时，上下文的大小可控，同时不忘记早期的要求，也能理解"那个桶""刚才加的树"这类指代。
4. **两层测评**：程序检查硬约束（完成度、回归、保持率），LLM 裁判评**效果**（好不好、像不像、协不协调），裁判本身要经过人工校准。

**非目标（这一版不做）**：图形界面、撤销 / 重做的交互、多人协作、训练。

## 3. 用户场景示例

```
第 1 轮  在 10 m × 10 m 的草地上搭一个低多边形小村庄：一座小屋（墙、斜屋顶、门、两扇窗）、一口石井、两棵树。
第 2 轮  在小屋东边约 3 米处加一个木头栅栏围起来的小菜园，里面有三排菜。
第 3 轮  把小屋的屋顶改成红色瓦片。
第 4 轮  加一条从小屋门口通到石井的碎石小路。
第 5 轮  再加三棵树，种在村庄北边，不要挡住小路。
第 6 轮  去掉菜园的栅栏，菜保留。
第 7 轮  在石井旁边放一个木桶，贴着井的外壁。
第 8 轮  把刚才那个桶换成两个小一点的。
```
到第 8 轮，场景大约有 80–150 个物体，脚本大约 1000–1500 行。第 8 轮的"刚才那个桶"需要指代消解。

## 4. Workflow 怎么改

### 4.1 现在的流程（一次建模，一条需求）

```
run_build(prompt)
  └─ _Build
       round0:     Coder.run(prompt) → 渲染 → Critic(prompt)            → 存档 round0
       revise(k):  Coder.run(refine(prompt, issues)) → 渲染 → diff → Verifier → 存档 round{k}
       learn → finalize
```

### 4.2 改造后的流程：三层循环

```
run_session(turns)                                  ← 第 1 层：会话（新增，workflow/session.py）
  for 每一轮用户需求 k:
     ┌─ plan_turn       ① 更新需求账本 ② 指代消解 ③ 生成本轮任务说明             （新）
     ├─ edit            Coder 在当前脚本上修改，结束时声明"本轮改了哪些物体"      ← 第 2 层：轮内闭环（复用 _Build）
     ├─ review          渲染 → Critic（本轮需求 + 账本 + 场景登记表）
     ├─ revise(1..N)    没通过 → Coder 修改 → 场景差异 + 回归报告 → Verifier
     ├─ close_turn      轮末快照 → 回归报告 → 更新场景登记表和轮次日志           （新）
     └─ 存档 t{k}_done
         每一次 Coder.run() 内部：现有的 agent loop + rails + 上下文引擎        ← 第 3 层：agent loop（不改）
  finalize_session → session.json（每轮的记录、成本、上下文长度）
```

**关键决定：每一轮内部复用现有的 `_Build`，而不是另写一套。** 具体做法是把 `_Build` 的 `round0` 拆成两种入口：
- `round0_new(prompt)`：现在的行为，用于第 1 轮；
- `round0_edit(task)`：在已有的 `current_script` 上修改，用于第 2 轮起。

`revise`、Critic、Verifier、存档的逻辑全部复用。这样**单轮建模就是"只有一轮的会话"**，原来的测评和实验都不受影响。

### 4.3 每一轮的阶段

| 阶段 | 做什么 | 谁来做 | 成本 |
|---|---|---|---|
| **plan_turn** | ① 账本管理员：输入旧账本和新需求，输出新增、取代、不变的条目；② 指代消解：把"那个桶""刚才加的树"解析成具体的物体名（查场景登记表和轮次日志）；③ 拼出本轮任务说明 | 一次 Haiku 调用，输出 JSON；之后用程序检查（见 5.4） | 约 $0.002 |
| **edit** | Coder 修改脚本；结束前**必须调用 `declare_changes(added, modified, removed, reason)`** 声明本轮改了什么 | Coder（Sonnet） | 主要成本 |
| **review** | 渲染 4 个视角 → Critic 对照"本轮需求 + 账本"挑问题 | Critic（Haiku） | 很低 |
| **revise** | 和现在一样，另外多一份**回归报告**：Coder 声明之外、却发生了变化的物体 | Coder + Verifier | 视情况 |
| **close_turn** | 轮末快照 → 计算本轮的场景差异 → 更新场景登记表（程序）→ 写一行轮次日志（程序，用模板生成，不调用 LLM）→ 存档 | 程序 | 0 |

**`declare_changes` 为什么重要**：
1. **交互使用时没有标准答案**（测评里才有 `touches`），只能拿 Coder 的声明和实际的场景差异做比较："声明之外的变化"就是可疑的回归，交给 Verifier 判断；
2. 场景登记表需要知道"哪个物体是为了哪条需求加的"；
3. 测评时，"声明"和"实际差异"的一致率本身就是一个过程指标：Coder 是否清楚自己改了什么。

| 文件 | 改动 |

### 4.5 存档、分叉和接口

- 每一轮结束存档 `t{k}_done`，轮内修改轮存档 `t{k}_round{r}`；从任意一轮之后分叉：`fork_from=(run_dir, "t04_done")`；
- 做策略对比时，所有策略**从同一个第 1 轮结果分叉**，起点完全相同，第 1 轮也只花一次钱。

**需求是逐轮输入的，系统看不到后面的轮次。**
- 交互模式：真人看完上一轮的结果，再输入下一轮；
- 测评模式：`run_session` 手里有整个会话文件，但**严格按顺序**，每次只把第 k 轮需求的**字符串**交给系统，等这一轮完全结束（含修改轮和存档）再交下一轮。会话文件里的 `expect`、`touches`、`persist`、`requires`、细则清单**只有测评脚本和离线裁判能看到**；
- **用测试保证不偷看未来**：断言第 k 轮所有 LLM 请求的内容里，不出现第 k+1 轮及之后的需求原文，也不出现任何检查项。

```python
run_session(turns, cfg: SessionConfig, run_dir, resume=False, fork_from=None) -> dict   # 测评用
s = Session.start(first_request, cfg, run_dir); s.turn("把屋顶改成红色"); s.fork("t03_done").turn("改成蓝色")
```
`SessionConfig` = `BuildConfig` + `memory: "history" | "structured" | "structured+retrieval"`（对应 M0 / M2 / M3）。

## 5. 上下文与记忆管理（核心）

### 5.1 问题：到底是什么在膨胀

| 会膨胀的东西 | 第 1 轮 | 第 8 轮（估计） | 现在怎么处理 |
|---|---|---|---|
| 用户需求的原文 | 1 条 | 8 条，约 1–2k token | 只有一条 |
| **脚本** | 200–300 行，约 3–5k token（新基线实测） | 1000–1500 行，约 **20–35k token** | 整份常驻在上下文末尾 |
| 场景 | 20–40 个物体 | 80–150 个物体，`inspect_scene` 约 8–15k token | 按需调用 |
| 轮内的工具调用历史 | 每轮新开一次 `coder.run()`，自然清零 | 同左 | 上下文引擎：压缩旧脚本、常驻当前脚本、预算守卫 |
| 评审意见 | 每轮最多 3 条 | 需要知道"早期哪些问题已经接受过" | 只在一次建模内传递 |

**结论**：多轮时，真正的压力**不在对话历史，而在脚本和场景本身**。很多"多轮记忆"方案只做了"对话摘要"，这里不够用。

### 5.2 三个要解决的子问题

1. **记住用户要什么**：早期的要求不能丢，被推翻的旧要求不能再执行（屋顶从棕色改成红色之后，就不能再按"棕色"检查）；
2. **知道场景里有什么**：哪个物体是什么、为了哪条需求加的、由脚本的哪个函数生成，用于指代消解和局部修改；
3. **只看需要看的代码**：脚本很长时，Coder 不需要每一轮都看到全部 1500 行。

### 5.3 分层记忆：六层，按"变化快慢"排列

| 层 | 内容 | 类型 | 怎么写入 | 谁读 | 预算 |
|---|---|---|---|---|---|
| **L0 规则** | 系统提示词 + 修改规则 | 静态 | — | Coder、Critic | 约 1.5k |
| **L1 需求账本** | 有效需求的结构化列表，带来源轮次和状态（有效 / 已取代） | **语义记忆** | plan_turn，账本管理员（Haiku）+ 程序检查 | Coder、Critic、裁判 | ≤ 1.5k |
| **L2 场景登记表** | 物体分组（"小屋：墙、屋顶、门……"）→ 对应哪条需求 → 由哪个函数生成 → 位置和尺寸摘要 | **世界状态** | close_turn，**程序从快照生成** + Coder 的声明 | Coder、指代消解 | ≤ 3k |
| **L3 轮次日志** | 每轮一行："第 7 轮：加木桶 → 新增 Well_Bucket，Critic 通过，无回归" | **情景记忆** | close_turn，**程序按模板生成** | Coder、指代消解 | ≤ 1k |
| **L4 当前脚本** | 小于阈值（约 12k token）时整份常驻；超过阈值后，常驻**大纲**（函数列表 + 文档字符串 + 行号范围），具体代码用 `view_section(name)` 按需加载 | 工作区 | 每次执行成功后更新（已有） | Coder | 全文 ≤ 12k，否则大纲 ≤ 3k + 按需 |
| **L5 轮内工作记忆** | 本轮的工具调用历史 | 短期记忆 | agent loop（已有） | Coder | 上下文引擎 + 预算守卫（已有） |

**排列顺序就是 prompt 的顺序**：L0（不变）→ L1（偶尔变）→ L2/L3（每轮追加）→ 本轮任务 → L4（每步都可能变）→ L5。越稳定的越靠前，**prompt 缓存的命中率越高**。L1 在中间变化时，后面的内容都会失效，所以 L1 采用"只追加、用状态标记取代"的方式更新，尽量不改写已有条目。

**为什么 L2、L3 由程序生成，不用 LLM 写摘要**：LLM 写的摘要可能**编造**场景里没有的东西，而且一旦写错，之后每一轮都会被错误的记忆误导。场景快照才是真实情况，所以登记表**每一轮都从快照重新生成**，而不是在旧记录上累积修改。

**脚本的结构约束（L4 的前提）**：修改规则要求脚本按部件组织成函数（`build_house()`、`build_well()`……），最后由一个 `build_scene()` 调用。这样：
- 大纲有意义，可以按需加载某个函数的代码；
- 场景登记表能把物体对应到函数；
- 局部修改的范围更容易控制，回归更少。

### 5.4 写入时的防护：账本不能"悄悄丢东西"

账本管理员每次输出后，用程序检查：
1. 旧账本里的每一条有效条目，**要么保留，要么被明确标记为"已取代"并给出理由**，不能凭空消失；
2. 新增的条目必须能在本轮需求原文里找到依据；
3. 指代消解的结果，必须是场景登记表里**真实存在的物体名**。

任何一条不满足，就重试一次；还不满足，就退回"把新需求原文直接追加到账本"，保证不丢信息。测评里有标准账本，可以直接算出账本更新的准确率。

### 5.5 指代消解

"刚才那个桶""北边的树""那条小路"——在 plan_turn 里解析：
- 输入：本轮需求 + L2 场景登记表 + L3 轮次日志；
- 输出：本轮任务说明里写明具体的物体名，例如"把 `Well_Bucket` 替换为两个更小的桶，保持贴着井的外壁"；
- 如果有歧义（比如有两个桶），在任务说明里列出候选，让 Coder 用 `inspect_scene` 确认，不让账本管理员瞎猜。

### 5.6 每个角色看到什么

| 角色 | 看到的内容 |
|---|---|
| Coder | L0 + L1 + L2 + L3 + 本轮任务说明（含指代消解结果）+ L4 + L5 |
| Critic | 本轮需求 + L1 账本 + 渲染图 + 场景摘要；规则："重点检查本轮需求；早期的要求只检查有没有被破坏；不要因为早期已经接受的风格而拒绝" |
| Verifier | 本轮要修的问题 + 修改前后的渲染图 + 场景差异 + **回归报告** |
| 裁判（离线） | 见 6.2 |

### 5.7 对照实验：端到端只比 3 组，组件各自用指标测

所有策略**从同一个第 1 轮结果分叉**：

| 策略 | 内容 | 重复次数 |
|---|---|---|
| **M0 完整历史** | 所有需求原文 + 整份脚本 | 2 |
| **M2 结构化记忆** | L1 账本 + L2 场景登记表 + L3 轮次日志 + 整份脚本 | 2 |
| **M3 结构化记忆 + 检索** | M2 + L4 脚本大纲 + 按需检索代码段 | **1** |

**两个主要问题，各对应一组对比**：
1. **M0 vs M2**：结构化记忆能不能减少回归、更好地保持早期需求？这是主要结论，需要足够的样本，所以跑 2 次；
2. **M2 vs M3**：用检索代替整份脚本，能不能在**质量不明显下降**的前提下省上下文和成本？它要回答的是"省了多少、有没有明显变差"，对样本量的要求更低，所以只跑 1 次。

**不为每个组件单独设消融组**，而是用组件自己的指标来测：

| 组件 | 指标 | 标准答案从哪来 | 成本 |
|---|---|---|---|
| 需求账本 | 账本更新准确率（有没有漏条目、取代得对不对） | 会话文件里的标准账本 | 0 |
| 指代消解 | 解析准确率 | 会话文件里的 `refs` | 0 |
| 代码检索 | recall@k；关键词 / 向量 / 混合三种方式的对比 | Coder 实际修改的函数 | **0：在 M2 的轨迹上离线重放** |

**检索可以离线测**：M2 的每一轮都有完整的记录（本轮任务 + Coder 实际改了哪些函数），把检索器在这些记录上重放一遍，就能算出 recall@k，不需要再跑任何建模。所以 M3 这一组只负责回答端到端的问题。

原来的"只有账本"一组（M1）去掉了：它想回答的"账本有没有用"，由账本更新准确率和 M0 vs M2 的对比共同回答。

每种策略都记录：回归率、需求保持率、每轮上下文 token 数、缓存命中率、成本。

### 5.8 面试时可能被追问的问题

| 追问 | 回答要点 |
|---|---|
| 为什么不直接把历史对话做摘要？ | 摘要可能编造、会累积误差；而且多轮时真正大的不是对话，是脚本和场景。所以按"用户意图 / 世界状态 / 事件 / 代码"分层，后两者由程序从真实快照生成 |
| 为什么不对历史做 RAG 检索？ | 需求账本是**全部都要遵守**的约束，不是"找几条相关的"；漏检一条就是一次需求违背。所以账本全部放进上下文，检索只用在代码按需加载、指代消解、标出相关需求这三处（5.9） |
| 检索效果怎么评估？ | 用 Coder 实际修改的函数当标准答案，算 recall@k，不需要人工标注；再对比关键词、向量、混合三种检索 |
| 为什么用 SQLite + numpy，不用向量数据库？ | 一个会话只有几百条，暴力计算就够快；和存档放在一起，分叉时整份复制，状态一致。规模变大再换 |
| 怎么防止遗忘？ | 账本只追加、用状态标记取代；写入时有程序检查；测评里用"需求保持率"直接测量 |
| 被推翻的需求怎么处理？ | 账本条目有"已取代"状态并指向新条目，Critic 和裁判都只检查有效条目 |
| 上下文压缩和 prompt 缓存怎么权衡？ | 按变化快慢排列各层；账本只追加；现有的上下文引擎也是"每块内容只在过期时压缩一次"，减少缓存失效 |
| 怎么证明记忆方案有效？ | 端到端只比两组：M0 vs M2（记忆）、M2 vs M3（检索），同一个起点分叉，按会话配对 + bootstrap；各组件用自己的指标测（账本准确率、指代消解准确率、检索 recall@k），这样能定位是哪个组件起作用，又不用为每个组件都跑一组昂贵的实验 |

## 6. 测评：三层

### 6.1 第一层：程序检查（硬约束）

每一轮写好期望的变化，基于场景快照检查，纯 Python：

| 检查 | 含义 |
|---|---|
| `exists` / `absent` / `count` | 名字匹配某个模式的物体存在 / 不存在 / 数量在范围内 |
| `near` / `on` / `direction` | 间隙、上下关系、方位（+x 为东，+y 为北） |
| `grounded` | 最低点在地面上 |
| `above` | A 整体在 B 的上方，水平方向有重叠（画在床头上方） |
| `contains_xy` | A 的水平范围包住 B（地毯在床下面并露出两边） |
| `evenly_spaced` | 一组物体沿某个轴等距，间距的变化在容差以内 |
| `material_hue` | 材质的基础颜色落在某个色相范围 |
| `touches` | 本轮**允许**改动的物体名模式；其余物体的变化都算回归 |
| `persist` | 之后一直要成立的检查，用来测需求保持率 |
| `requires` | 这一轮依赖前面哪些检查（例：第 6 轮"去掉菜园的栅栏"依赖第 2 轮的"菜园存在"）。前置没满足时，这一轮**照常执行**，但记为"前置失败"，单独统计，不计入完成率 |

名字用宽松的模式匹配（审计显示 3664 个物体都有有意义的名字）；匹配不上的记为"无法判定"，单独统计。

### 6.2 第二层：LLM-as-judge（效果）

程序检查只能回答"有没有、在不在、颜色对不对"，回答不了"**好不好看、像不像、整体协不协调、改得是否克制**"。这一层用 LLM 裁判来评。下面的设计参考了几种业界常用的做法：

| 做法 | 出处 | 核心思路 | 这里借鉴什么 |
|---|---|---|---|
| **问题分解（QG/A）+ 依赖图** | DSG（ICLR 2024，Google）、TIFA | 把需求拆成**原子问题**（实体、属性、关系各一个），组织成依赖图；父问题答"否"，子问题就不再问，避免自相矛盾的回答 | 本轮细则清单的结构，以及"前置失败"的处理 |
| **两两比较 + Elo** | GPTEval3D（CVPR 2024） | 让多模态模型比较两个 3D 结果，按多个维度各选一个更好的，再换算成 Elo；对输入做扰动、多次取平均来降噪 | 策略对比的方式和维度 |
| **二元细则 + 整体打分** | BlenderWorld（223 个任务、2651 条细则） | 每个任务写很多条"是 / 否"细则，再加一个整体质量分，两者融合 | 细则和打分两条线并行 |
| **人类偏好的 Elo** | 3DCodeArena、LMArena | 人做两两比较，Bradley–Terry 拟合，bootstrap 置信区间 | 人工校准的形式 |
| **裁判的偏差** | MT-Bench（LLM-as-a-judge） | 位置偏好、偏爱更长的回答、偏爱自己家族的模型 | 交换顺序、换不同家族的裁判 |
| **先推理再打分、带锚点的量表** | G-Eval、Prometheus | 每个分数都配有具体的描述，先写理由再给分 | 维度打分的写法 |

#### ① 本轮细则清单（每轮，原子问题 + 依赖）

出题时，把每一轮的需求拆成**原子问题**（每个问题只问一件事），并标出依赖关系：

```
本轮需求：在石井旁边放一个木桶，贴着井的外壁。
Q1  场景里有木桶吗？                             [实体]
Q2  木桶是木头材质的吗？                ← 依赖 Q1   [属性]
Q3  木桶贴着石井的外壁吗？              ← 依赖 Q1   [空间关系]
Q4  木桶立在地面上（没有悬空、没有插进井里）吗？ ← 依赖 Q1 [物理合理性]
Q5  木桶相对石井的大小合理吗？          ← 依赖 Q1   [比例]
P1  小屋、小路、菜园的位置和样子和上一轮一样吗？      [保持：上一轮之前的有效需求]
```
- **Q1 答"否"时，Q2–Q5 不再问，直接记为"否"**，避免出现"没有木桶，但木桶是木头的"这种矛盾回答（DSG 的做法）；
- 问题在**出题时就写好**，和程序检查的 `expect` 放在一起，不让裁判自己出题。出题可以先用 LLM 生成草稿，再人工审核；
- 程序能检查的问题（比如 Q1、Q4），同时用程序判一遍，**用来测裁判在有标准答案的问题上的准确率**；
- 指标：**细则通过率**，按问题类型（实体 / 属性 / 空间关系 / 物理合理性 / 比例 / 保持）分别统计。

#### ② 维度打分（每轮，1–5 分，带锚点）

以 GPTEval3D 的五个维度为基础，针对多轮编辑做了调整：

| 维度 | 对应 GPTEval3D | 1 分 | 3 分 | 5 分 |
|---|---|---|---|---|
| **本轮需求完成度** | 文本-资产对齐 | 没做或做错 | 做了，但有明显偏差 | 完全按要求做到 |
| **早期需求保持** | （多轮新增） | 多处早期要求被破坏 | 有一处被破坏 | 全部保持 |
| **修改克制度**（对比修改前后） | （多轮新增） | 大面积重做 | 改了一些不该改的 | 只改了要求的部分 |
| **空间与物理合理性** | 3D 合理性 | 多处悬空、穿插、比例失调 | 有一处明显问题 | 没有明显问题 |
| **几何细节** | 几何细节 | 像占位的方块和圆柱 | 能认出来，细节一般 | 形状有辨识度、细节到位 |
| **材质与整体协调** | 纹理细节 + 纹理-几何一致性 | 材质、风格与场景明显冲突 | 有些不协调 | 新加的部分和已有场景融为一体 |

- 输入：本轮需求、有效的账本、**修改前和修改后**各 4 张渲染图、本轮场景差异的摘要；
- 输出：每个维度**先写一两句依据，再给分**；
- 不设"总分"，各维度分别报告。合成一个总分会掩盖问题，比如"完成度很高但改坏了别的"。

#### ③ 两两比较（策略对比时用，GPTEval3D 的做法）

- 同一会话、同一轮，两种策略（比如 M0 和 M2）的结果并排给裁判，按上面 6 个维度**各选一个更好的**（A / B / 差不多）；
- **每一对都交换左右顺序再问一次**，两次不一致就记为"差不多"；
- 用 Bradley–Terry 拟合出各策略在每个维度上的 Elo，bootstrap 求置信区间。

#### 裁判本身的可靠性（必须做，否则分数不可信）

| 措施 | 针对什么 |
|---|---|
| **裁判用 GPT 或 Gemini**，和 Coder（Sonnet）、Critic（Haiku）不是同一家族 | 偏爱同族模型的输出 |
| 裁判和 Critic 分开，裁判的意见**永远不反馈给系统** | 系统迎合裁判（古德哈特定律） |
| 两两比较时交换顺序 | 位置偏好 |
| 每个样本评 3 次，报告标准差；波动大的维度降权或删除 | 打分不稳定 |
| 在程序能判断的细则上核对裁判的准确率 | 看图看错 |
| **人工校准**：抽 40–60 个样本，用校准页面让你独立标注，细则用 Cohen's κ、打分用 Spearman 相关；**一致率不够的维度不作为结论** | 裁判和人的判断不一致 |
| 报告里写明裁判模型、提示词版本、和人工的一致率 | 可复现 |

**成本**：每次调用约 8 张图 + 文本，约 $0.02–0.04；细则 + 打分各 3 次约 $0.15 一轮。一个 6 轮会话约 $1；3 个会话 × 3 种策略的试点约 $9。

### 6.3 第三层：人工

- 用于校准裁判（见上）；
- 每种策略抽几个完整会话，看最后一轮的渲染图，作为定性的案例。面试时可以展示"同一个会话，M0 和 M2 第 6 轮的结果对比"。

### 6.4 指标汇总

| 指标 | 层 | 用途 |
|---|---|---|
| **回归率** | 程序 | **主要指标之一** |
| **需求保持率** | 程序 | **主要指标之一** |
| 单轮完成率 | 程序 | 次要 |
| 本轮细则通过率 | 裁判 ① | 次要：程序测不到的语义完成度 |
| 各维度分数 | 裁判 ② | 次要：效果；只报告和人工一致率足够的维度 |
| 策略排名 | 裁判 ③ | 次要：整体偏好 |
| 指代消解准确率、账本更新准确率 | 程序（对照标准答案） | 记忆模块本身 |
| 声明与实际差异的一致率、整份重写的比例 | 程序 | 过程指标 |
| 每轮上下文 token、缓存命中率、成本、延迟 | trace | 成本 |
| 无法判定率 | 程序 | 测评本身的可靠性 |

### 6.5 实验计划

**主实验用固定脚本 + 前置条件**：所有策略面对完全相同的需求，配对比较才公平。

**试点（约 $30）**：3 个会话 × 6 轮 × M0、M2、M3 × 1 次，从同一个第 1 轮分叉，再加裁判评分。要回答：
- 程序检查的无法判定率够不够低？
- 回归率大概多少？各策略之间有没有差距的迹象？
- 检索 recall@k 大概多少（在 M2 的轨迹上离线重放）？M3 里检索漏掉代码时，会不会导致回归？
- 裁判的重复评分稳不稳定？

**正式实验（约 $65–75）**：8 个会话 × 6 轮 × （M0 × 2 次 + M2 × 2 次 + M3 × 1 次）= 240 轮；人工校准裁判；**预先注册**主要指标（回归率、需求保持率）和判定规则，按会话配对 + bootstrap。

**补充实验：模拟用户（定性，约 $15）**：真实用户会根据上一轮的结果决定下一步，比如"菜园再往东挪一点"，固定脚本做不到这一点。补充实验用一个 LLM 扮演用户：给它目标场景的描述和每一轮的渲染图，让它决定下一轮说什么，包括纠正。和 τ-bench 的用户模拟器思路相同。这组实验**不可复现**（不同策略看到的需求不一样），所以只做定性观察，不作为主要结论。这个模拟用户以后可以复用到个人助手和多轮 RL 上。

## 7. 风险和对策

| 风险 | 对策 |
|---|---|
| Coder 整份重写脚本，顺手改坏别的 | 修改规则 + 脚本按函数组织；回归报告打回修改轮；"整份重写的比例"作为过程指标 |
| 物体改名被误判为回归 | 规则要求保留名字；按"位置、尺寸、顶点数相同"识别改名，单独统计 |
| 名字匹配太脆弱 | 试点先测无法判定率；用 `declare_changes` 交叉核对 |
| 账本悄悄丢需求 | 写入时的程序检查（5.4）+ 需求保持率 |
| 裁判不可靠 | 重复评分、交换顺序、人工校准；一致率低的维度不用 |
| 场景变大后 Critic 变差 | 正好在复杂场景上校准 Critic |
| 工作量 | 实现顺序 M0 → M2 → M3；检索的质量先在 M2 的轨迹上离线验证，再接入 M3 |
